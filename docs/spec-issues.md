# Specification issues

Problems found in docs/spec (revision 1.13) while implementing. The spec is never edited here;
each entry records the location, the problem, the choice made and why (most conservative reading).

| ID | Location | Problem | Choice made | Why |
| --- | --- | --- | --- | --- |
| SI-01 | contracts/factory-tools*.schema.json `x-tools` | Tool manifests reference `./domain.schema.json#/$defs/...`. Resolved against the manifests' `$id` (`https://factory.example/spec/factory-tools/1.2.0`), that names `https://factory.example/spec/factory-tools/domain.schema.json`, not the domain `$id` `https://factory.example/spec/domain/2.0`. | Resolve the references file-relative (sibling file `domain.schema.json`), as tools/validate_spec.py does. | This doesn't change behaviour. The references sit inside an annotation keyword, so JSON Schema never dereferences them. |
| SI-02 | examples/ai-review (negatives without `expect`/`error`) | 8 schema-rejectable negatives and about 100 adversarial negatives state only `"expected": "reject"` or nothing. Their reason exists only in the file name. | For the 8 schema negatives, the expected Ajv path and keyword are derived from the file name (packages/contracts/test/fixture-catalog.ts `NAMED_SCHEMA_NEGATIVES`) and asserted. The adversarial ones are semantic and deferred to W-141–W-143. | A test can only check "rejected for the stated reason" if the reason is stated. Deriving it from the name is the most literal reading. |
| SI-03 | examples/ai-review/negative-enhanced-oracle-{automated,human_sampled}-{human,ai_only}.json; tools/review_mode_contracts.py | The generator copies a standard four-slot panel bundle and sets `assignment.assurance` to `enhanced`. The embedded AIReviewPanelAssignment is then schema-invalid (`/slots/2/role enum`), which has nothing to do with the stated reason (an enhanced oracle gate cannot be automated or sampled). | The fixtures stay semantic negatives, owned by W-141–W-143. Their `assignment` part is excluded from the wire-validity check through `INCIDENTALLY_INVALID_PARTS`. | If schema rejection were accepted as the reason, these fixtures would "pass" without the gate-mode rule they exist to exercise. |
| SI-04 | contracts/schema.sql `factory_tool_call.request_hash` | `CHECK(request_hash ~ '^[0-9a-f]64$')` matches one hex character followed by the literal "64". No real SHA-256 request digest can be stored, so the factory tool-call ledger cannot record a single call. | Migrations 0001–0010 keep the reference verbatim. Forward migration 0011 replaces the check with `'^[0-9a-f]{64}$'`. | The intent (64 lowercase hex characters, as for every other digest in chapter 02) is unambiguous. The fix only rejects values the typo accidentally allowed (e.g. `a64`). |
| SI-05 | contracts/schema.sql ownership block | It reassigns 8 of 9 functions to `factory_migrator` but omits `guard_environment_generation()`. When an administrator runs the script, that function stays owned by the administrator, against "Migration/admin credentials are separate". | The migrations run as `factory_migrator`, so it owns every object. The catalog-equality test asserts this is the only difference from the reference. | The reference intent (migrator owns everything) is stated explicitly. |
| SI-06 | contracts/schema.sql guard functions | The plpgsql guards reference factory tables unqualified (e.g. `task%ROWTYPE`) and do not pin `search_path`. They fail (`relation "task" does not exist`) for any session whose search_path omits `factory`, including the runtime login, and could resolve objects in another schema. | Forward migration 0012 sets `search_path = factory, pg_catalog` on all nine functions. Repositories still use schema-qualified names. | Pinning makes the existing functions behave as written, for every caller. It also closes the search-path substitution risk. |
| SI-07 | 03-api-events.md idempotency; contracts/schema.sql `idempotency_record` | The API "persists the request hash and original response for 7 days", but `UNIQUE(org_id, principal_id, route, request_key)` holds for the row's lifetime, runtime has no DELETE, and nothing says what a reused key means after 7 days. | An expired record still answers with the same rule (replay or 409) until the retention job deletes it. | This is the conservative reading: no window in which a stale key silently creates a second task. |
| SI-08 | 05-workflows-gates.md ReviewMode ("PR, outcome manifest/export … MUST carry ReviewMode"); examples/ai-review/positive-output-legacy.json | The prose requires every outcome manifest to carry ReviewMode, but the positive legacy fixture omits it and is accepted. The validator text in the same chapter only requires the mode "whenever AI authority or approval fields occur, even when the mode was omitted". | A manifest with no mode and no AI fields is a legacy human outcome, and the export labels it `human`. Any AI field without `ai_only` and the marker is rejected. Every manifest this build writes carries `reviewMode`. | This follows the stricter rule the spec states as checkable. It still rejects every AI-provenance negative, and our own outputs always meet the prose. |
| SI-09 | 03-api-events.md / contracts/openapi; 16-acceptance-catalogue AC-54; 12 "Audit interaction" | AC-54 is defined by an operator exporting an outcome bundle, but no endpoint, schema or role mapping exists for that export. | See A-14: a non-contract route and envelope built only from contract members, operator-only. | Without a route the acceptance criterion cannot be exercised. The envelope stays outside the contract set so it cannot be mistaken for one. |
| SI-10 | 06-runner-workspaces.md:59, :67; domain.schema.json | The setup profile's contents are required in prose and `setupProfileRef` is mandatory, but no `SetupProfile` schema exists. | A local document (`factory-setup-profile/1`) in `packages/workspace` that embeds the contract's `Recipe`. | The contract cannot be extended here; a local type keeps the prose requirements checkable without inventing wire semantics. |
| SI-11 | contracts/interfaces.ts:89-91; schema.sql `workspace`, `stage_run` | `allocateOrAttach` takes a `specHash` and chapter 06 requires 409 on a changed specHash, but only `execution_allocation` stores one. | Workspace conflict is decided by equality of the stored columns (task, repository, stage run, role, branch, base commit, setup profile). The run-level specHash is compared against the stage run's allocation rows (W-017). The workspace call checks the specHash's form and stores nothing. | A column cannot be added without a migration that breaks equality with the reference DDL; comparing every stored field still refuses every change a workspace row can express. |
| SI-13 | `06-runner-workspaces.md:14`, `:112` | Deterministic names are defined for allocation Jobs and PVCs, not for checkpoint Jobs. | `factory-` + base32(sha256(org id, receipt id))[:20] + `-c`. The name comes from `receipt_id`, so two controllers racing on one receipt collide on the 409 instead of on a counter. | A deterministic name from the receipt id makes two controllers racing on one receipt collide on the 409 instead of on a counter. |
| SI-14 | `contracts/interfaces.ts:78-79`; `execution_allocation.state` | `RunHandle.state` has six values and the allocation has nine; the mapping is not given. | `suspect`, `stopping` and `quarantined` report `reconciling`; `terminated` reports `cancelled` only when a cancel was requested. | The terminated state means two different things (a cancelled run, or a lost pod that gets a new generation), and only the cancel record can tell them apart. |
| SI-16 | domain.schema.json `RepositoryCandidate.treeDigest`, `Digest` | `treeDigest` is a 64-hex digest with no defined algorithm; a SHA-1 tree id is 40 hex. | `canonicalHash({ algorithm: 'factory-tree-digest/1', entries })` over one `FileSnapshot` per blob, sorted by the path's UTF-8 bytes, modes limited to 100644, 100755 and 120000, paths and symlink targets well-formed UTF-8. The vector is committed in `packages/workspace/src/tree-digest.ts`. | It matches AC-230's "raw object and file bytes" wording, needs no Git-specific object id, and W-020's reader can reproduce it from raw bytes. |
| SI-17 | 06-runner-workspaces.md:59, :100, :108; examples/kubernetes-job.json | Nothing says which container performs the first clone: the example mounts the workspace read-only in the supervisor and has no other trusted container. Separately, `:100` asks for `git worktree remove` on release, which would run Git on a candidate-writable repository against `:59`. | A trusted first step of the Job clones onto the empty volume (W-017's pod executor; W-018 ships the local one). Release deletes the whole generation without Git; `git worktree remove` is a sandbox-side action only and is not built. | `:59` forbids repository-local configuration running a program in a trusted allocation, and a worktree removal reads that configuration. |
| SI-18 | contracts/interfaces.ts:95-96; schema.sql `workspace`; `CandidateManifest` | `materializeCandidate` receives a candidate and a role, but each workspace row needs a stage run and a setup profile. The manifest's `createdByStageRunId` is the author's run, and no chapter says what `profileRefs` holds. | An optional fourth argument `binding: { stageRunId, setupProfileRef }` from the trusted caller; without it the call fails (`verifier_binding_required`). The stage run must belong to the manifest's task, carry the same role, not be superseded and not be the author's. Workspace ids are version-8 UUIDs derived from SHA-256 of organization, candidate, repository, role and stage run. | The method stays assignable to the reference interface, the verifier's own run is recorded rather than the author's, and a retry finds the same rows and directories. |
| SI-19 | `06-runner-workspaces.md:13`, `:23`; `schema.sql` `execution_allocation.controller_lease_until` | Step 3 records "a controller lease" and the supervisor has a 60-second lease, but there is one timestamp column, no column naming a holder, and nothing says which lease the column is. | One deadline, that of the current phase: the start deadline in `desired` and `starting`, the writer's lease in `running` and `suspect` (each accepted heartbeat puts it 60 s ahead), the stop deadline in `stopping`. Controllers do not exclude each other by it (section 5, rule 2). | One column cannot hold three clocks; the phase decides which one it is, and every judgement is made in SQL on clock_timestamp(). |
| SI-20 | `contracts/interfaces.ts:84`; `06-runner-workspaces.md:90`; `schema.sql` `execution_allocation` | `cancel` carries a command id and a reason and "sets desired cancellation", but the row has no column for either, `stopping` does not say why, and a cancel can arrive before any allocation exists. | One cancel record per stage run, as an `audit_event` row written under the stage run's lock, with or without an allocation (D18). The allocate step refuses after it, and SI-14's `cancelled` reads it. The stop reason is a second, diagnostic audit row. | The cancel must exist with or without an allocation and be read by the allocate step; an audit row at a deterministic id is the only place that needs no migration and cannot be undone by the runtime role. |
| SI-21 | `06-runner-workspaces.md:5`, `:14`; `contracts/interfaces.ts:81` | `specHash` is "immutable" and compared, but nothing defines what it is a hash of or who computes it. | Opaque to the runner: 64 hex from the caller, bound by the first allocation, compared on every later call. W-023 defines its contents. The runner separately annotates a digest of the manifest it rendered, for diagnosis only. | The runner only needs equality, which is what the spec asks it to enforce. |
| SI-22 | `06-runner-workspaces.md:11`; `04-temporal.md:57`; `schema.sql` `stage_run` | Step 1 says "insert or lock the stage_run row", but the workflow persists run intent first, and the row needs an `input_ref` that `StageInput` does not carry. | The runner locks only. | SI-23 | `StageInput.workspaceId`; `execution_allocation.workspace_id`; `contracts/interfaces.ts:95-96` | An allocation and a stage input each name one workspace, while `materializeCandidate` returns one per repository. | SI-24 | `06-runner-workspaces.md:16`, `:110`; `examples/kubernetes-job.json`; `execution_allocation.supervisor_identity` | The writer claim must be "pod-specific" and the identity "allocation-specific", but the example uses one fixed audience, and no chapter says how the runner learns which pod is calling or what `supervisor_identity` holds. | A projected token with the audience `factory-allocation:<org id>:<allocation id>`, checked by token review on every call; the review must list that audience; pod name and UID come from the token's binding and from nowhere else; the pod is then read, and must exist and be owned by the allocation's Job. | SI-25 | `06-runner-workspaces.md:13-14`, `:59`; SI-17 | SI-17's trusted first step has no stated way to return its result: pods cannot reach the database, and the step holds no identity. | The init container's termination message under `terminationMessagePolicy: File`, read by the runner from pod status and accepted in a second phase: a receipt only with exit code 0.
