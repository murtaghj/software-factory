# Acceptance and test strategy

C1 covers valid cancellation and rejection of an already fulfilled order. C2 covers replay and simultaneous distinct requests. C3 covers ownership denial. C4 covers durable audit history. Dependency outage recovery also exercises C1/C2.

S1–S7 below specify the exact expected outcomes. Use isolated synthetic customers/orders and a controllable inventory stub. Run the API and database together for transaction assertions; exercise the worker for recovery. Preserve existing contract/regression tests. Execute in a separate verifier checkout with authenticated discovery/execution counts. Run the canonical acceptance controller outside the candidate process against the isolated fixture API; private cases remain outside candidate access. Evidence labels distinguish in-process integrity checks from out-of-process behavior. Enhanced assurance is required by the new API, authenticated ownership checks and persistent migration. Independently accept the oracle before implementation and run fresh adversarial authorization, migration and retry tests against the exact candidate; these remain planned, not yet proven. Feature baseline red is useful but not mandatory; no planned scenario is a passing result.
