# 05 — Work types, gates, modes and rework

## Shared stage contract

Each stage takes StageInput with a versioned input binding, context/candidate/artifact refs, role, allowed tools, budget and return targets. It returns a StageOutcome: runner StageResult or ControllerStageResult, with `completed`, `product_failure`, `inconclusive`, `needs_input`, `infrastructure_error` or `cancelled`, plus outputs, findings, usage and provenance. “Completed” means that stage produced its contracted output; only the gate evaluator establishes task progression. Runner results carry allocationEpoch and producerKind runner; controller results carry producerKind controller and use operation/record preconditions without inventing a pod epoch. Both require authenticated provenance and the exact stage input binding.

Stage roles are discovery, planner, criteria_author, implementer, reviewer, adversarial_tester, verifier, publisher and knowledge_curator. Reviewer and verifier receive independently selected context and workspace access. Process separation and artifact authority are required for independence; a single model family cannot by itself establish it. Judgement roles (reviewer, oracle reviewer, intent challenger) SHOULD use a qualified model family different from the author where one is available, and record the family used (chapter 20); the D5 AI panel MUST meet the stronger family-diversity requirement below.

The rules-role-content/1.0 profile resolves rules before plan approval, validates admitted role content before stage allocation, and rechecks exception/admission validity at gates and delivery. Changes follow existing invalidation/replan paths; no new workflow stage or human-floor exemption is introduced. See [chapter 21](21-rules-role-content-skills.md) for the authoritative requirements and compatibility rules.

## Common nodes

| Node | Output and completion gate | Return target |
| --- | --- | --- |
| intake | Accepted TaskSpec, initial type/risk/scope and allowed resources; input is actionable or a concrete clarification is requested. | Requester clarification. |
| discover | App/repository/dependency snapshot, evidence-backed scope and a ContextManifest of sources consulted, prior-incident matches and blocking/nonblocking gaps; uncertainty explicitly recorded. | Intake if goal changes. |
| plan | Complete engineering packet and proposed DAG, including design, impact, criteria, scenario matrix, DoD, risks, implementation sequence and delivery/recovery. | Discover or intake. |
| plan_peer_review | Independent primary and required specialists approve the exact packet under the applicable ReviewMode; plan_peer_approved and plan_accepted. | Author/design/criteria owner with anchored findings. |
| execute | Candidate code/config/document/report and portable progress handoff; expected files/artifacts exist. | Plan if approach invalid. |
| evaluate | Work-specific independent evidence for the exact candidate and environment. | Execute, criteria or discovery by classified failure. |
| review | Scoped skeptical findings and a revision-bound review result; blocking findings resolved. | Execute, plan or intake. |
| render_design | Design scope only: deterministic Markdown rendering of the exact approved packet with stable section/criterion/scenario anchors. | Plan review if the approved subject changed. |
| deliver | Requested report/patch/PR/preview/release or rendered design recorded, with required current gates. | Integration/execute if source changes; render for design. |
| pr_review | Reconcile the explicit PR-completion policy, accepted recipe no-change branch or scoped non-PR outcome; delivery_complete. | Findings return by category; changed human head requires reconciliation. |
| learn_close | Outcome manifest, knowledge proposals, cost and durable resource lifecycle. | Missing evidence or cleanup ownership. |

Peer review is mandatory for the substantive work in every path and every assurance/invocation mode. Plan length follows scope and applicability; missing sections do not become optional. Initial authorized read-only discovery can proceed to prepare a reviewable plan. [Chapter 19](19-peer-plan-review.md) defines complete packet coverage and layered presentation.

The following paths specialize these nodes. Every task instantiates exact stage kinds rather than passing an unstructured “do the next thing” prompt. The common discover node is specialized by the template’s discovery-role nodes: diagnose produces the ContextManifest in bug_fix 3.0.0, impact (feature_impact) in existing_feature 3.0.0, and brief (product_brief) in greenfield 4.0.0, with interview (intent_interview) adding evidence; scope_accepted at confirm_intent reads that manifest’s blocking gaps.

## Greenfield path

Feature intent with new_application selects greenfield; feature intent with existing_application selects existing_feature. Bug intent with existing_application selects bug_fix. These are distinct pinned templates over the shared stages, not prompt variants. [Chapter 17](17-project-journeys.md) defines the complete journey, contracts, bootstrap and return paths.

Seed brief → adaptive human interview → independent intent challenge → exact-brief confirmation under ReviewMode → author foundation design and complete plan → independent peer sign-off under ReviewMode → reconcile repository/bootstrap to a real base → scaffold in an isolated worktree → independently verify foundation → register experimental application/profiles → author/review acceptance criteria → implement and independently verify a vertical slice → compose bounded typed children → verify integrated parent outcomes → review and scoped delivery.

A new application has no previous behavior to make deliberately red. Foundation readiness and product acceptance are separate requirements. New components in existing monorepos still take this path, while preserving existing repository/consumer obligations. Child failure or incompatible integration returns to the affected design/implementation stage; weak acceptance returns to criteria review. A small complete slice can justify zero extra children but still requires integrated parent verification.

## Feature in an existing project path

Example: add order cancellation while preserving the order audit history.

| Stage | Required evidence | Failure/rework |
| --- | --- | --- |
| Discover requirements | Actors, user journeys, success/failure behavior, permissions, data/API expectations and excluded behavior. | Ambiguity → intake; unknown affected service → discovery. |
| Design and plan | Complete approach, contracts/migrations, implementation sequence, scenarios/criteria mapping, definition of done and rollout/recovery; independent peers approve the exact packet under ReviewMode. | Incompatible contract or review finding → design. |
| Establish acceptance package | Reviewed scenarios, fixtures and checks with criteria IDs; intended expected results. Baseline execution where meaningful. | Weak oracle → criteria review. |
| Implement | Candidate manifest and focused diff; local feedback attached. | Changed requirements → scope. |
| Verify | Acceptance, affected contracts and regressions executed; no undisclosed skip. | Candidate defect → implementation. |
| Skeptical/adversarial review | Behavior, negative cases and relevant threats examined according to policy. | Finding → implementation/design. |
| Integrate/deliver | Current candidate passes integration and requested environment/release checks. | Moving base → integration candidate and reverify. |

A deliberately failing baseline is useful for some features but is not universally required. The locked expectations cannot be silently weakened to accept an incomplete feature.

## Bug path

Example: checkout retries create duplicate reservations.

1. Reconstruct the failing application journey and actual service versions using registry, telemetry and controlled reproduction. Maintain competing root-cause hypotheses.
2. Define the correct behavior from contracts/requirements. Before test-package authoring/repair, obtain independent peer sign-off on the complete investigation/repair design, red/lock/green scenarios, acceptance criteria and definition of done. Then create the regression tests, fixtures, helpers and recipe in a dedicated workspace.
3. Independently review the oracle. Run the package against pinned baseline B in a controlled environment. Require the intended assertion failure, not a compile/setup/network error. Capture failure signature and discovered/executed test counts.
4. Freeze the reviewed package by content hash after red is demonstrated. Store its approved canonical copy outside implementer write authority. Implementation receives a readable copy or scoped failure evidence according to policy.
5. Implement candidate C on a task branch. The implementer cannot change the authoritative package. For verified-fix delivery, C MUST contain a permanent-suite regression test copied from the locked package or a declared equivalent derived from it, unless an owner records a retention exception (chapter 24).
6. In a separate verifier checkout, materialize C and the exact locked package. Require green and affected broader regressions under comparable fixtures/dependencies/configuration. Before accepting green, also run C's in-tree test and confirm content-hash equality with the locked test or, for a declared equivalent, the same scenario and intended assertion going red on B and green on C. A retention exception does not waive locked-package red/green. Record any justified environmental difference.
7. Review the causal explanation and repair, exercise relevant adversarial cases, integrate and deliver per scope.

If reproduction is impossible, produce an inconclusive investigation or request evidence; do not close as verified fixed. If the original oracle is wrong, return to test review, create a new package version and repeat baseline red. Keep the original result. No assurance mode may waive this bug invariant. Environment-only bugs establish red and green through the deployment provider with isolated equivalent state. A workaround and a root-cause repair are distinct outcomes and must match the accepted ticket scope.

Bug diagnosis computes a normalized failure signature and checks prior incidents; matches are labelled hypotheses among the competing ones and never replace reproduction or red/lock/green. A verified fix keeps its regression test in the permanent suite, records a reviewer-confirmed root-cause category and, by default in standard and enhanced assurance, triggers read-only variant analysis. Recurring categories raise systemic proposals. See [chapter 24](24-context-gathering-incident-learning.md).

From W-033 pilot qualification onward, diagnosis and investigation MUST run under the hypothesis ledger: each hypothesis declares a prediction, kill criterion and timebox, the supervisor enforces timeboxes and detects stalls, and fresh-eyes checkpoints and early human questions intervene at defined points. W-107 alone MAY produce its DiagnosisManifest from the chapter 08 hypothesis table before W-122 ledger tools exist; its ContextManifest, failure signature, regression memory and human/evidence gates remain required. Security findings enter as bug or maintenance tasks with a security flag, severity target and, when embargoed, confidential handling. See [chapter 26](26-investigation-discipline.md) and [chapter 25](25-data-security-operational-safeguards.md).

## Refactor path

Discover structural objective → enumerate preserved behavior/contracts → review characterization suite → establish passing baseline → refactor → compare candidate behavior → independent structural review → integrate/deliver.

Preserved invariants include public outputs, error behavior, side effects, ordering and operational properties relevant to the task. Do not encode a known defect as intended behavior without explicit scope. A passing suite alone does not prove the structural goal: reviewer checks architecture/diff against that goal. Unexpected behavior change returns to implementation; a desired behavior change becomes a linked feature/bug task with separate criteria. Inadequate characterization returns to criteria and reruns both baseline and candidate.

## Maintenance path

Inventory current dependencies/toolchain → select explicit target versions → read authoritative migration/compatibility guidance → establish working baseline matrix → update lockfiles/code/config → verify supported matrix and consumers → review supply-chain/compatibility changes → integrate/deliver.

Pin package sources/checksums, runtime/OS/architecture combinations and consumer versions. Tests cover startup and representative integration, not only successful install. Deprecated APIs, database formats or generated clients add migration/contract gates. A target version failing a supported consumer returns to upgrade assessment; an implementation mistake returns to execution. Record intentional support-policy changes for owner decision rather than quietly shrinking the matrix.

## Performance path

Define metric/workload/target and correctness guardrails → freeze benchmark protocol → measure baseline → plan/implement → measure candidate under comparable conditions → statistical and correctness review → load/rollout observation when requested.

Protocol records hardware class, CPU/memory limits, runtime/configuration, data set, warmup, concurrency, duration, repetitions and noise controls. Default starting protocol is five baseline and five candidate trials with interleaved order where feasible; the performance owner sets an adequate sample size before seeing results. Store distributions, not only a best run. Accept only when the predeclared target and variability criterion hold and error/correctness/resource guardrails pass. Inconclusive noise returns to measurement design; regressions return to implementation. A new workload/protocol invalidates comparability and requires a new baseline.

## Platform/infrastructure/data path

Describe desired state and invariants → inventory resources/data/dependencies → plan forward change and recovery → validate IaC/migrations → rehearse against representative isolated state → review operational/data evidence → publish artifact → apply when authorized → observe and reconcile actual state.

Criteria include schema compatibility, data integrity, rollout sequencing, concurrent old/new application versions, backup/restore requirements and irreversible operations. A code rollback is not a data rollback. Where reverse migration is unsafe, specify roll-forward or restore with an explicit loss window. Failed rehearsal returns to design/implementation. Unknown apply status triggers provider reconciliation, not another apply. Production application requires qualified provider capabilities and release policy; PR-only delivery ends after publishing reviewed artifacts.

## Documentation path

Define audience/questions/version → select authoritative sources → outline/draft → validate claims, links, rendered structure and applicable runnable examples → fresh subject review → publish documentation artifact/PR → propose knowledge refresh.

No application test run is required merely because a Markdown file changed. Runnable API examples and operational commands must be checked in the declared environment where feasible; unexecuted examples are labeled with the reason. Unsupported claims return to source selection; wording/usability failures return to drafting. A source version change invalidates affected claim reviews. Documentation and runbook content cannot silently redefine execution policy.

## Investigation path

Bound question/decision/time budget → plan discriminating experiments → gather evidence and compare hypotheses/alternatives → synthesize report → independent evidence review → deliver decision material and clean up experiments.

Success is a reviewed answer to the agreed scope, which may explicitly conclude insufficient evidence within the agreed boundary. A report must distinguish observations, inference and open questions and retain negative experiments. It must not claim certainty just because time expired. No PR/implementation/deploy is implied. If a prototype is useful it lives in an experiment workspace and is labeled nonproduction. Follow-up changes become linked tasks.

## Mixed work and several repositories

The parent owns shared intent, delivery scope, total budget and candidate composition. Children own typed evidence. Example: API feature depends on a schema platform child and documentation child. Reject cycles; default maximum 8 active child workflows across a root task tree, depth 2 below the root and 2 concurrently authoring children per parent, under the separate organization caps; changes require explicit capacity review. Split by independent responsibility, not by arbitrary token chunks. Parent success requires all mandatory children and integrated evidence against the same release composition. Optional child failure is reported with the predeclared optionality reason; it is not relabeled optional after failure.

A campaign is a parent initiative applying one approved change-recipe version to a pinned target set. Its packet satisfies peer sign-off at campaign level per chapter 23; targets are ordinary child tasks with typed recipe outcomes (`changed`, `already_compliant`, `not_applicable`, `needs_judgement`). Campaign targets count against active-child limits, while the total target count is bounded by the approved campaign. Deterministic transforms produce the same evidence and pass the same gates as agentic execution. See [chapter 23](23-readiness-recipes-campaigns.md).

## Assurance, invocation and delivery policy

| Axis | Values | Resolution rule |
| --- | --- | --- |
| Work type | Eight types above | Request proposes; discovery validates; mixed scope splits. |
| Target context | new_application, existing_application | Intake declares; discovery validates; work type plus context selects a compatible versioned template. Greenfield is new-target feature intent in v2. |
| Assurance | fast, standard, enhanced | Default standard; effective level is maximum of requested, app minimum and discovered risk. |
| ReviewMode | human (default), ai_only | Per-application joint human decision; independent of assurance; ai_only fails closed under D5. |
| Invocation budget | one or bounded | One allows one execution invocation for the selected authoring unit; independent checks still run. Unmet criteria finish incomplete or await an authorized budget change. |
| Delivery | report, patch, pr, preview, production, design | Defaults: report for investigation, pr for other source changes. Docs allow report/patch/pr. Design allows feature, refactor, performance and platform only and is always explicit. Production always explicit. |

Fast eligibility requires an application allowlist (including an explicit draft-application grant if greenfield), narrow understood scope and no elevated risk trigger. It uses concise artifacts and cheaper qualified evaluators within the same required journey graph, preserving work-specific criteria, independent evaluation and revision binding. No assurance or invocation mode removes a mandatory stage. Standard increases plan/evidence depth and skeptical outcome review; plan sign-off under ReviewMode exists in every tier. Enhanced adds specialist and adversarial gates chosen for the actual risk. Greenfield intent confirmation and engineering peer plan sign-off are always required for their applicable stages. Other human decisions are required when configured or when resolving scope/authority; agents cannot fabricate them.

Resolve delivery scope against the accepted outcome before building the graph. A feature request whose criterion is working functionality cannot be marked complete by returning only a proposal: either select patch/PR/environment delivery or explicitly revise the accepted goal to analysis and route it through investigation. A report can describe incomplete work, but that task outcome remains incomplete. Patch/PR scopes still require the relevant code evidence; they omit release/merge nodes, but MUST prepare a verification environment when an accepted criterion requires one. Preview adds environment evidence. Production adds authorization, actual release and observation. Documentation report scope delivers the accepted document artifact. Design scope explicitly changes the accepted outcome to an approved, delivered design; it cannot satisfy a working-functionality criterion, and a build needs a separate linked task.

Risk triggers: public API/consumer change, authentication/authorization/payment/data sensitivity, persistent data migration, several services, unknown blast radius, critical app, privileged infrastructure change or substantial performance/resource risk. Evaluate at intake, discovery, plan and actual diff/artifact. Automatic increases are allowed; reductions require a recorded authorized policy decision and cannot remove INV-05, provenance or access invariants.

## Design-only delivery

A requester MAY select delivery scope `design` for feature intent (greenfield or existing_feature), refactor, performance or platform intent. Investigation and documentation keep their own report/document outcomes; bug and maintenance work do not offer design scope. Design is a delivery scope, not a ninth work type (ADR-34): work type, target context, assurance, invocation and delivery remain independent axes (ADR-06). The selected work type still determines discovery, packet content, risk triggers and specialist routing; only the stopping point and delivered artifact change. A separate work type would duplicate every type's planning rules and lose the type that a later build must match.

Selecting design pins the design template for that work type and target under the design-delivery/1.0 profile ([chapter 17](17-project-journeys.md)): intake → discovery/ContextManifest (scope_accepted) → for greenfield, product brief, interview, independent challenge and intent_confirmation (intent_aligned) → plan or foundation_design → plan_peer_review (architecture_accepted, plan_peer_approved and plan_accepted from the independent primary and every required specialist under ReviewMode) → render_design → deliver → delivery_complete → learn_close. architecture_accepted is required in every design template because the design is the delivered product.

A design graph MUST NOT contain implementation, test-package authoring, test execution against code, bootstrap, scaffold, preview, integration, merge or release nodes, MUST NOT request workspace or environment write capability, and MUST NOT require oracle, baseline, outcome, review_passed or integration gates. Discovery stays authorized read-only; render and delivery are trusted controller stages, so no coding workspace or harness coding stage is allocated. Proportional tiers apply, but every chapter 19 section remains required: acceptance_tests is the planned scenario matrix for the future build and definition_of_done names that build's evidence and PlanReviewPacket.plannedBuildDeliveryScope. Fast assurance, one invocation or a single qualified runtime never removes architecture_accepted, plan_peer_approved, plan_accepted, intent_aligned for greenfield or any required specialist. The D5 panel may supply these gates only under an in-force ai_only decision; embargoed and hotfix work stay human.

render_design MUST deterministically render the exact approved packet to Markdown with a pinned renderer version, stable section/criterion/scenario anchors and a reproducible digest bound to the approved subject. A newer packet revision, missing anchor or digest mismatch blocks delivery. [Chapter 10](10-delivery-environments.md) defines the design PR and report targets. The OutcomeManifest records `design_approved` and MUST NOT claim delivered, verified_fix, implemented, verified or outcome_verified; planned scenarios stay planned.

Design tasks reserve against a separate `design` budget class (PolicyProfile.designBudget; budget_account.budget_class). Initial defaults: USD 10 estimated model allowance, 6 authoring invocations, 2 hours active execution, 14 days calendar lifetime and 2 design returns. These are calibration seeds. Design spend never draws on an implementation budget; a later build has its own budget. Exhaustion finishes incomplete with the last packet revision and unmet gates and never delivers an unapproved design. Rules resolve before plan approval and are rechecked at delivery; rule exceptions keep their human approval ([chapter 21](21-rules-role-content-skills.md)).

An embargoed design (TaskRequest.security.embargoed=true) follows D4: human review only and delivery only to the task's private_fork/separate_repo PublicationTarget for its security group, with provider-enforced reader checks before every push (INT-15), or a restricted confidential_report. A security-flagged design that is not embargoed follows ordinary delivery but stays in human review mode, never ai_only. A build of an embargoed design inherits its security group (chapter 19). INV-28 applies to the rendered packet: it carries the highest classification of its sources and the delivery target classification MUST permit it; otherwise delivery blocks for an authorized owner decision and never downgrades content.

A running task cannot move into or out of design scope; amend_spec and request_delivery reject that with 422 design_scope_change_requires_new_task. “Build from this design” creates a new linked implementation task; [chapter 19](19-peer-plan-review.md) defines when it may reuse the approved packet. Template versions and compatibility are in chapter 17. Rendering, delivery and binding behavior are **not yet proven** by these static fixtures.

## Draft-preview preparation

Where accepted checks need a PR-generated environment, the qualified profile permits a trusted controller preparation step before evaluation (including foundation, candidate-green and rework verification). It records deterministic secret-scan, scope/protected-path, classification/embargo and same-repository identity admission, then publishes only an open draft PR with the preview label. Failed/unknown admission blocks publication; embargoed tasks never use this path. This is an environment prerequisite inside the existing verification/controller flow, not completion of deliver or a waiver of plan/intent/oracle prerequisites. It does not reorder the mandatory gate graph or silently alter pinned histories; enable it only in a qualified behavior release/profile.

The draft is preview_only and cannot satisfy pr_created or review/delivery gates. Independent checks run against the current EnvironmentPlan generation, exact head SHA and image digests; only all current candidate gates passing authorizes ready-for-review. Every new commit invalidates dependent evidence and returns the PR to draft for that revision; factory rework converts it before pushing, then repeats admission, preview reconciliation and verification. See chapter 10 for operation/head fences and chapter 04 for continuation. Deterministic preview admission is separate from behavioral verification; a successful label mutation, deployment or readiness check cannot manufacture a passed outcome/review gate.

## Limits and stopping

Initial defaults: 3 semantic attempts per execution node, 2 returns to discovery/design, 8 total authoring invocations, 4 hours active execution, 7 days calendar lifetime, and USD 25 estimated model allowance per ordinary task. These are policy seeds for calibration, not claims about likely cost. Investigation may set a tighter research budget. Design tasks use the separate design budget class below. Provider usage may be delayed; reservation and hard process limits bound exposure, but a precise money ceiling requires provider-side enforcement. Stop before new work if capacity/reservation is unavailable. A stopped task includes the last valid checkpoint, unmet gates, actual spend/uncertainty and required next decision.

## Proportional scrutiny and review authority

Tier selection uses policy signals: declared and actual changed paths/size, application criticality, dependency/service reach, migrations, auth/payment/data sensitivity, coverage provenance and uncertainty. A small diff is not proof of low risk; unknown coverage/blast radius escalates. Model opinions may suggest evidence but never set or lower the tier. Reassess at intake, discovery, accepted plan and actual candidate; automatic escalation invalidates insufficient evidence before reviewable publication; preliminary draft publication still requires its current deterministic admission checks. Reductions require a recorded authorized decision.

| Tier | Eligibility | Required review (human by default; D5 AI panel when in force) | Additional evaluation |
| --- | --- | --- | --- |
| Fast | Allowlisted application/change class; small within declared limits; understood reproduction or outcome; no risk trigger | Independent pre-implementation peer on a concise complete packet/structure outline; pilot bug/feature oracle approval; ordinary PR review before merge | Canonical checks, protected-path tamper check, scope assessment and one qualified independent review; bounded feedback |
| Standard | Default | Independent plan peer; pilot bug/feature oracle approval; ordinary PR review before merge | Targeted mutation strength where applicable; distinct qualified model family for judgement when available; independently authored acceptance cases |
| Enhanced | Auth, payment, persistent migration, several services, critical application, uncertain blast radius or other risk trigger | Full packet with specialists, human oracle and PR review | Adversarial cases and independently operated out-of-process checks where the outcome is executable; required environment capability must be available or the work remains inconclusive |

All tiers retain complete applicable 12-section coverage, exact bindings, independent verification, budget/call caps and bug red → lock → green. A small packet may use short entries and reasoned applicability; the structure outline is its first engineering view. Greenfield retains intent and design sign-off under ReviewMode. Human PR review is a merge condition in human mode; the D5 panel replaces it only for eligible ai_only dev merges. A pr_created task, or a design task at its design PR, may meet its narrower delivery objective before that review. Fast/one never remove plan_peer_approved, intent_aligned when applicable, or pilot human oracle floors outside D5.

Versioned per-cohort GateMode rules support human, human_sampled and automated for eligible judgement gates, plus ai_panel only under an in-force D5 decision. MANDATORY_HUMAN_GATES remains the default floor for architecture, plan acceptance/plan_peer_approved, greenfield intent and release authority. GateModeRule enforces these floors by gateId even when humanFloor is false; only the D5 panel resolver may substitute ai_panel for replaceable review gates. A rule reference alone is insufficient: the service MUST resolve current authority, scope and qualification, not accept a schema-valid rule as permission. release_authorized is always human. Pilot bug/feature and enhanced oracle_accepted remain human outside D5. Later policy owners may qualify other eligible oracle/review modes from ledger evidence. Sampling is selected by the control plane before execution, persisted across retries and hidden from agent control; sampled fast work runs standard scrutiny. All samples, including misses/disagreements, enter the ledger. Gate mode changes never waive deterministic integrity requirements or convert a model opinion into human approval.

## Opt-in ai_only review mode (D5)

For a new repository, ReviewModeDecision.repositoryBindingState=pre_repository binds the human-owned draft application and an organization-approved repositoryIntentPolicyRef (allowed provider/installation/namespace and bootstrap constraints), plus the intended dev branch and scoped factory identity. It authorizes eligible review gates before bootstrap, without a fabricated repository ID or branch-protection receipt. After the approved bootstrap creates the real repository, the bootstrap controller MUST append ReviewModeRepositoryBinding linking the same decision/application/policy to the immutable bootstrap receipt, real repository and verified branch/identity protection. The review/merge controller refuses PR review authority and every AI merge until this binding is effective; ordinary bootstrap authority remains separate. Existing repositories use repositoryBindingState=bound with repository/protection evidence at establishment. Missing policy, scope, receipt, protection or current authority blocks; no pending binding grants merge permission.

ReviewMode is per application, defaults to human and is independent of fast, standard or enhanced assurance. D5 (29 October 2026) amends D1 only for opted-in applications. An immutable ReviewModeDecision MUST bind application (including a draft application before greenfield work), permitted work/change/path scope, all eligible tiers, qualification cohort, policy, validity interval, rollback/degradation thresholds and both authenticated human decisions: policy owner AND application owner. It is never earned automatically or established/relaxed by a rule. Multi-application work MUST have in-force authority for every affected application; otherwise its shared reviews remain human. Urgent hotfix (D2) and embargoed security work (D4/INT-15) are ineligible.

Before establishment, every reviewer and adjudicator configuration MUST pass ReviewerQualification on a versioned corpus containing clean and seeded-defect plans AND PRs, with predeclared catch-rate and false-approval thresholds, denominators and results by defect class/severity. Include applicable intent, oracle and specialist cases for the roles being qualified. Failure or missing evidence blocks establishment. Pin model family/release, prompt/role content, tools, evaluator and behavior release. Any change suspends ai_only, creates a new qualification cohort and requires requalification plus a fresh joint human decision. Panel effectiveness is **not yet proven**; static fixtures establish neither real catch rates nor independence in practice.

Each replaced gate (intent_aligned, architecture_accepted, plan_accepted, plan_peer_approved, oracle_accepted and human PR review as a merge condition) MUST use at least two independent AI reviewers, with at least two model families in the panel and at least one family different from the authoring stage. Family labels and independence MUST derive from authenticated stage/configuration evidence, never reviewer assertions. Fresh isolated contexts preserve INV-07; reviewers MUST NOT see one another’s verdicts before submitting immutable decisions. Plan and oracle reviews add a distinct adversarial reviewer explicitly prompted to refute. Every required specialist/owner review slot in chapters 19/21 gets a specialist-role AI reviewer with the same scope and full context; none is dropped. Enhanced uses at least three base reviewers (larger than fast/standard), plus the adversarial and required specialist slots, and retains all additional adversarial cases and out-of-process evidence.

The evaluator requires every assigned member to approve the exact immutable subject and assignment, including INV-22 bindings; no majority, timeout or missing response can pass. A blocking finding can be rejected only through the existing bounded rebuttal/adjudication path, using a separately qualified AI adjudicator configuration independent of author and panel. Adjudication does not count as a missing panel vote or rewrite a verdict: reviewers must submit new decisions for the current round/subject after resolution. Unresolved disagreement after the existing bound (default one rebuttal cycle and one adjudication) escalates the task to a human and blocks it; no automatic approval. Greenfield confirmation compares the brief to the requester’s own submitted answers; material ambiguity or stakeholder conflict still asks that human and blocks intent_aligned.

release_authorized ALWAYS requires a human. INV-05 red → lock → green, INV-07 author/verdict separation, canonical checks, protected-path tamper/scope checks, mutation strength where applicable, independent verification, budgets and INV-28 classification remain floors. Rule exceptions, scope changes, disclosure decisions and privilege grants retain their existing human authority. AI approval is an AIReviewDecision, never a human decision field (INV-29). PR, outcome manifest/export (AC-54) and UI MUST carry ReviewMode and the visible marker “AI-reviewed — no human review”; voluntary human review is recorded and displayed separately without relabelling AI approvals.

Revocation, expiry, emergency stop and authorized degradation automatically resolve the application to human mode and manual human merge. Read failure or unknown decision/qualification state fails closed. The controller MUST serialize mode transitions with admission/publication/merge, fence pending effects and re-evaluate all affected nonterminal work under human requirements before any further publication or merge; historical decisions are retained. Clearing a stop never restores ai_only. Chapter 11 defines the post-merge audit and degradation ledger; chapter 10 limits automatic merges to the configured dev/integration branch and qualified previews.

The trusted policy resolver MUST check qualification.evaluatedAt ≤ each owner approvedAt ≤ decision.validFrom ≤ evaluation time < expiresAt. Future-dated approvals never establish current authority. Its contextual GateModeRule resolver MUST reject automated and human_sampled oracle_accepted for enhanced assurance in every mode; only human or a currently in-force ai_panel may pass. The review coordinator resolves every nested human approval reference through ArtifactStore, authenticates its human provenance and rejects AI, unknown, cyclic or mismatched refs, including PlanApprovalSet/IntentApprovalSet and voluntary reviews. The publication/export service requires ReviewMode and the AI marker whenever AI authority or approval fields occur, even when the mode was omitted; it also verifies outcome completion and referenced votes fall within effective authority. These cross-record checks are modeled by tools/review_mode_validation.py, and design outputs use the same predicates: tools/design_delivery_validation.py resolves every AI design gate approval through its panel bundle (in_force, panel_ready and chronology at approval and delivery), every human design approval and human outcome reference through human_provenance_ready, and the design OutcomeManifest through output_ready. JSON Schema alone cannot resolve authority, timestamps or referenced provenance.

Authority is resolved once, from trusted control-plane state, for the whole output. The task snapshot (applications, repositories, change class, assurance, embargo, incident/hotfix flags and delivery target) comes from the control plane; an exported TaskView or other projection never overrides it. The current ReviewModeDecision state (revocation, emergency stop, cohort, qualification) is evaluated at the root, and a nested review bundle cannot carry or revive its own authority state. Provider review observations (PR review state and observation refs) are evidence about the provider, never human approval; human PR approval requires a resolved human decision record. Any effect on production, including an incomplete or mitigation outcome, requires human release_authorized evidence with an identified, authenticated decider. The reference predicates in tools/review_mode_validation.py are a static model of these rules; they do not prove runtime enforcement, and the runtime corpus required by W-141/W-143 MUST include these cases.

## Reproduction, trivial changes and unreproduced proposals

The bug lane includes a dedicated regression-authoring stage. A versioned FailureSignatureProfile classifies intended assertion failure separately from compile, fixture, discovery, infrastructure and timeout failure for each supported framework. Baseline evidence binds parser version, named scenario, expected assertion/matcher and executed counts; unknown signatures are inconclusive. An oracle-reviewed shim may bridge a missing interface only if it is immutable, identical on baseline/candidate and cannot implement the repair or fake the assertion. Unsupported baseline interfaces may instead require an external contract-level reproduction. Green is accepted only against the same locked package/shim and comparable environment.

Message text is observable behavior: use an exact string, snapshot or contract assertion when appropriate. A genuinely nonbehavioral maintenance/docs change can be reclassified through an explicit amended intent; it cannot be relabeled merely to bypass INV-05.

If reproduction fails, default to investigation/requested evidence. An owner may authorize a distinct bounded proposal via propose_unreproduced_fix, bound to diagnosis, candidate scope and explicit limitations. The proposal graph/template definition and its compiler rules remain a W-082 deliverable, not a supported branch of bug_fix 3.0.0. Before enabling it, W-082 MUST define and separately qualify normal plan peer review, independent available regressions, tamper/scope checks and PR-only publication without manufacturing baseline_valid, canonical_package_locked or outcome_verified for the bug. Record fix_proposed_unreproduced and incomplete, never verified_fix or auto-merge/deploy. This assisted exception is excluded from the M3 machine-reported-bug pilot; W-082 qualifies it before enabling it.
