# 03 — API, commands, events and authorization

## Transport conventions

Base path `/v2`; API description version 2.5.0. Deploy compatible validators/readers before enabling these contract revisions; retained artifacts and workflow histories keep their pinned semantics. JSON UTF-8. OIDC bearer token for callers; workload identity/mTLS for internal components. Organization comes from authorized identity context and route scope, never from trusting a payload field alone. Default request maximum 256 KiB; artifact uploads use the artifact protocol. Responses include request ID; errors use `application/problem+json` with `code`, `detail`, `requestId`, `retryable` and optional field errors. Never return raw provider credentials or prompts in an error.

All mutating public requests require `Idempotency-Key`, scoped to organization+principal+route. Persist the request hash and original response for 7 days; keep task/operation natural identity constraints for the resource lifetime. Same key/same hash returns the original resource; same key/different hash returns 409. Dedupe command IDs for the entire task lifetime. UI retries after a timeout must reuse the key.

Commands affecting an existing task require `If-Match` with its task-spec/control revision. A stale revision returns 412. Revision checks occur in the authoritative workflow command handler as well as the API; an HTTP precheck alone is race-prone. Immutable artifact IDs are never PATCHed.

## Greenfield interview API

GET /tasks/{taskId}/intent returns IntentInterviewView. POST /tasks/{taskId}/intent/answers accepts IntentAnswerRequest and returns 202 CommandReceipt; require Idempotency-Key, If-Match, current task-control revision and interview revision. The equivalent answer_intent command reaches the same serialized workflow handler. Authenticate the human at ingress; persist raw answers and their interpretation separately. A model or service identity cannot submit a human answer or human confirmation. D5 confirmation uses distinct AI records.

An unknown question ID or malformed answer is 422; a stale task/interview revision is 412; a conflicting duplicate command is 409. Check again when applying the command, and preserve submitted/unsent text for explicit reconciliation. GET on a task with no interview returns 404 interview_not_started. No response text or interpretation is itself a completed alignment decision.

In human mode, final confirmation uses the existing decision response endpoint with action confirm_intent and the exact IntentConfirmationSubject hash. The subject identifies the proposed normalized TaskSpec through its brief. Separate decision requests bind requiredPrincipalId for each required human owner; the complete set must approve the same subject. Approval checks configured human ownership, unresolved issues and current revisions before applying the spec/plan idempotently; it never expands tool authority. [Chapter 18](18-intent-interview.md) supplies the full protocol.

## Engineering peer review API

GET /tasks/{taskId}/plan-review returns PlanReviewView (404 review_not_started before preparation). GET /tasks/{taskId}/plan-review/comments returns a paginated subject-bound history. POST to that comments path accepts PlanReviewCommentRequest and returns 202 CommandReceipt, requiring Idempotency-Key/If-Match and expected control revision. comment_plan uses the same command handler. Authenticate human comment authors, validate section/criterion/scenario anchors and preserve original subject bindings. Assigned peers may raise blockers; other permitted contributors submit questions/suggestions for adjudication.

approve_plan decisions use only the existing response endpoint and requiredPrincipalId; respond_decision rejects them with 422 decision_requires_response_endpoint. DecisionResponse.reviewedSectionIds must cover the caller's assigned sections; reviewNotes hold anchored human findings. Approval rejects authors/service identities, stale packet/assignment/policy, missing peers and unresolved blocking findings. A scope acknowledgement is an auditable human claim, not proof inferred from clicking/reading telemetry. resolve_plan_comment references the comment, current subject and resolution artifact; only the originating peer or an explicitly delegated qualified independent reviewer may resolve a blocking comment.

Comments, resolutions and approvals are serialized in the same workflow command stream. The API projection cannot permit an arriving approval to skip a pending blocking change. See [chapter 19](19-peer-plan-review.md) for packet coverage, human independence, aggregation and revision behavior.

## Target admission and draft concurrency

Validate target.kind/workType compatibility, primary ID membership, tenant/application access, current draft revision/ref and any supplied repository intent. New-target RepositoryIntent can be omitted while interviewing; a resolved authorized intent is required in BootstrapPlan before side effects. new_application accepts feature only; bug requires an existing registered target. Return 422 for invalid combinations, 412 for a stale draft revision and 409 for a conflicting unresolved bootstrap claim. If-Match for draft changes refers to the draft revision and must agree with expectedRevision. Lock the application row while comparing/publishing revisions or claiming onboarding. Draft edits never rewrite a running snapshot.

Draft creation requires the organization-scoped create-application grant and assignable accountable owners. Repository creation additionally requires a qualified provider installation, allowed namespace, visibility and initialization template. Check those grants again before side effects. Idempotent draft creation reserves the key; idempotent task creation reserves its claim and launch outbox. Neither route creates repositories or deploys. Existing /applications routes return registered definitions only; incomplete identities remain on draft routes.

An amendment may expand/reclassify scope only through a new TaskSpec and plan. Once a task has acquired a repository/bootstrap side effect, changing its primary target identity is rejected; reconcile/cancel and create a linked task. This prevents orphaning the original claim. Template resolution and registration are emitted as versioned plan/application events with artifact refs, not as client-authored gate results.

## Commands and safe application

| Command | Preconditions | Effect |
| --- | --- | --- |
| `pause` | queued, running, waiting_input or waiting_decision; authorized owner/operator; cancelling is an idempotent no-op | Stop scheduling new stages; checkpoint/cancel active execution at the next bounded safe point; reconcile external operations. |
| `resume` | paused and current policy permits | Revalidate inputs, budget and artifacts; return to the recorded pre-pause state. Waiting states advance only by their own input/decision events. |
| `cancel` | accepted, queued, running, waiting_input, waiting_decision or paused; a repeat in cancelling is idempotent | Enter cancelling, prevent new writes, reconcile active operations, request cleanup, finish cancelled with actual side effects recorded. |
| `comment_plan` | Permitted human; current task and review subject; valid anchor | Append durable review note and route blocking findings; cannot directly edit a gate. |
| `resolve_plan_comment` | Authorized independent reviewer; bound comment/subject and resolution artifact | Append audited resolution; preserve prior text and require reevaluation of current review readiness. |
| `answer_intent` | Authenticated permitted human; current control/interview revision and pending question IDs | Append immutable answers, revise interview state and supersede stale confirmation; does not itself approve the brief. |
| `amend_spec` | Nonterminal; explicit new spec ref | Increment spec/plan revision, reassess scope/policy and invalidate dependent stages. In-flight old results are historical only. A change into or out of design scope is rejected (422 design_scope_change_requires_new_task). |
| `reassign_owner` | Current owner or authorized operator; nonterminal task; new principal has current tenant/application task-owner authority | Set ownerPrincipalId and append task.owner_changed with previous/new principals, reason and authority. Does not transfer a live workspace. |
| `take_over` | Authorized human owner/operator; queued, running, waiting_input, waiting_decision or paused; no current interactive holder; current EpochTransfer binding | Pause, stop writer, checkpoint and transfer epoch, then set interactiveHolderPrincipalId to the authenticated caller and append task.taken_over. |
| `hand_back` | paused; current interactive holder or authorized human operator; current EpochTransfer binding and ownership transfer proven | Transfer to a new automation epoch, clear interactiveHolderPrincipalId and append task.handed_back; reevaluate dependent evidence. |
| `change_budget` | Authorized budget owner | Reserve/increase/decrease future allowance; a decrease cannot erase actual charges. |
| `change_harness` | Allowed provider/model and safe boundary | Checkpoint, terminate/revoke old writer, create fresh session on current source; increment execution attempt when execution restarts. |
| `respond_decision` | Correct role, current binding, unexpired request; response requires only outcome, reason and subjectHash beyond common command/revision fields | Append decision and wake workflow. Duplicate identical response is idempotent; conflicting second response is rejected. |
| `retry_stage` | Failed/inconclusive stage and policy/budget permit | New semantic attempt, preserving earlier outcome; never force-success. |
| `request_delivery` | Authorized scope expansion and current candidate | Replan delivery/gates; new decision if required. Cannot directly set delivered status. Moving into or out of design scope is rejected with 422 design_scope_change_requires_new_task. |

Allowed states are defined by the [task state machine](04-temporal.md#task-state-machine). EpochTransfer binds workspaceId, expectedEpoch, checkpointRef and targetRef (authorized branch/workspace destination). For hand_back, checkpointRef MUST capture the returned source. The controller MUST quiesce the writer, verify checkpoint ownership and the expected epoch, then durably capture current source before transfer (hand_back MUST match the returned checkpoint), revoke the old writer and fence the new epoch before acknowledging transfer; a stale checkpoint or epoch is rejected. Hand-back leaves the task paused for explicit resume and revalidation.

confirm_intent, approve_plan and approve_rule_exception responses MUST use POST /decisions/{decisionId}/responses. The workflow handler rejects them on respond_decision with 422 decision_requires_response_endpoint; it MUST reject any other action requiring response fields unavailable on CommandEnvelope.

API inserts command+dispatch record transactionally. Dispatcher invokes a Temporal Update with a stable commandId. An Update timeout or lost response leaves the command in `delivered` (never `rejected`); the dispatcher re-invokes the Update with the same commandId until the workflow's receipt lookup reports `accepted`, `applied` or `rejected`. Reconcile by commandId; the workflow tracks applied/rejected command IDs across Continue-As-New via a durable receipt lookup before applying effects. Handler concurrency is serialized for mutations to the plan/spec/approval subject. Wait for active handlers before Continue-As-New. External webhooks are persisted then delivered as Signals with event IDs; Signals are hints to reconcile actual provider state, never proof of gate success. [Temporal message passing](https://docs.temporal.io/develop/typescript/workflows/message-passing)

Rule exception approvals use the existing decision endpoint with action approve_rule_exception and one exact required human principal per decision. Rule/skill revocations use authenticated control-plane decisions and ordinary durable events; they are not model tools. Factory tool 1.1 and retained 1.0 manifests are separately negotiated. See [chapter 21](21-rules-role-content-skills.md) for the authoritative requirements and compatibility rules.

## Event envelope and ordering

Fields: `eventId`, `orgId`, `taskId`, `sequence`, `eventType`, `occurredAt`, `recordedAt`, `source`, `correlationId`, `payloadRef` and `schemaVersion`. Sequence is assigned transactionally per task. Provider event time is not ordering authority. Types include task.accepted, plan.resolved, stage.started, stage.progress, stage.completed, gate.evaluated, decision.requested, decision.resolved, workspace.checkpointed, delivery.changed, cleanup.changed, budget.changed and task.completed.

SSE carries compact summary payloads and artifact references, not raw token streams. `id` equals task event sequence, distinct from the workflow projection sequence. Clients deduplicate and resume with Last-Event-ID or the nonnegative `after` query parameter; Last-Event-ID takes precedence when both are present. Send a keepalive every 15 seconds. If the cursor predates retained events, return 410 EventCursorExpired before opening the stream, with snapshotUrl and resumeAfterSequence and a matching Location header. snapshotUrl resolves GET /tasks/{taskId}; resumeAfterSequence records lastEventSequence at the expiry response. Fetch the current authorized TaskView and resume after its lastEventSequence, which MUST be at least resumeAfterSequence. A slow client can reconnect; do not hold unlimited buffers. Raw harness events live in chunked artifacts retrieved through the authorized run-log and artifact endpoints.

## Standard errors

400 malformed request; 401 unauthenticated; 403 insufficient scope; 404 unknown or inaccessible resource; 409 idempotency/state conflict; 410 event cursor expired with snapshot recovery fields; 412 stale revision; 413 oversize; 422 invalid schema/unsupported work combination; 429 admission/provider quota with Retry-After; 503 dependency unavailable. Product test failure is a run outcome, not HTTP 500. Unknown remote state is exposed as `reconciling`/`needs_operator`, never converted to “not found” without a provider check.

## Audit and external effects

Audit successful and rejected sensitive commands, artifact access to restricted transcripts, policy changes and delivery actions. Bind identity at ingress and revalidate current authority before delayed release. Revoked authority cannot be revived by replaying an old command. Record evaluated policy version and subject hash. Use request IDs in logs; never use high-cardinality task IDs as metric labels.

## PR review and policy commands

GET /tasks/{taskId}/pr-review returns the current PRReviewView, or 404 pr_review_not_started. TaskRequest.prCompletion selects pr_created, review_completed or merged and bounded review settings. The UI must show the selected outcome before intake acceptance. A later change requires amend_spec and reapproval of affected scope/DoD; it cannot silently lengthen a PR-only task or acquire merge authority.

Signed PR webhooks enter the existing inbox and become deduplicated reconciliation Signals. Fetch provider review state and exact head before interpreting approvals, changes requested, comments, merge or close. Map the external reviewer to an authorized identity/role. Ordinary comments are suggestions until triaged; text alone is never an instruction with authority. Human branch edits require a bound reconcile_pr_head decision whose ReconcilePrHeadSubject includes repository identity, observedHead, expectedHead, candidateRef, policyRef and resolution adopt or handover; the approval hashes that exact resolution, and changed heads invalidate it; handover_pr and propose_unreproduced_fix decisions use the existing exact-subject decision path, with current candidate, task/policy and limits in the subject.

Application health reads are application-scoped. Autonomy policy changes use reviewed policy/configuration releases in v1, with authenticated policy owners and application owners, a signed AutonomyPolicyDecision artifact and an append-only database record. For a jointly authorized human revision, authorityRef MUST reference both the policy owner's and the application owner's authenticated decisions for that revision; automatic tightening retains its previously authorized rule reference. There is no agent-writable policy mutation endpoint. factory_tool.proposed, factory_tool.finalized, pr_review.changed and pr_review.round_completed are task events. application_health.measured denotes insertion of an application_health_sample exposed through the application-scoped health read endpoint; it is not a task event and MAY also have an audit_event. policy.tightened records an autonomy_policy_decision and audit_event, then emits a task_event carrying the decision ref for each nonterminal task in the affected cohort whose admission or publication it holds. Cohort matching uses the behavior release, adapter/model profile, application and change class in chapter 22. Each task event carries bounded refs, never free-form tool output in Temporal history.


## Operator and campaign controls

The dashboard backend calls the internal OperatorControlPlane interface in contracts/interfaces.ts with authenticated human context and mTLS. It is not a model tool or a public /operations polling route. readEmergencyStop returns the organization-scoped EmergencyStopState; activateEmergencyStop requires an operator, a reason and expectedRevision. clearEmergencyStop requires a current operator human decision bound to the active stateRef digest and expectedRevision; the controller creates an immutable EmergencyStopDecision from the authenticated actor, rather than accepting a caller-supplied decider. Unknown, stale or unauthorized state fails closed (409 state conflict, 412 stale revision or 403 authority denied).

The controller uses the authorized organization_controller/emergency_stop upload scope for EmergencyStopRecord and EmergencyStopDecision, without a task/stage binding. It serializes activation/clearance under the organization lock, persists the new immutable EmergencyStopRecord artifact and audit_event with its monotonic revision and previous-state ref, and acknowledges only after durable commit. Retry the same OperationKey to recover the original result; a conflicting request hash is rejected. Trusted organization setup records revision zero as inactive; absence of initialized state holds work. The latest committed revision is authoritative; admission, publication and delivery MUST check it before effects, including while task workflows are paused or unavailable. State read failure holds work. Activation dispatches cancellation/reconciliation durably; clearance never invents completion evidence or resumes tasks automatically. Cohort stop-the-line clearance and gate-mode changes use the reviewed policy/configuration-release path above, with bound human policy-owner decisions and visible halt state; they do not require a fabricated taskId.

A campaign is represented by a parent task: GET /tasks/{taskId} exposes CampaignState and its immutable CampaignManifest, and the existing task event stream carries progress. pause/cancel use the parent task commands. Campaign plan approval uses approve_plan with all required chapter 19 peers; threshold clearance uses a resume_campaign decision on the parent task. A manual resume restores waiting_decision while that decision is pending. Onboarding owner confirmation uses confirm_application_owners on the onboarding task; embargo lifting uses lift_embargo on the security task and is restricted to its authorized security group. These exact-subject actions use the existing decision response endpoint and current task revision. No action relaxes peer-review or publication requirements.

DecisionView.action uses DecisionAction. Other configured task decisions use authorize_release for an exact release/environment, approve_oracle for the exact test package, accept_residual_risk for a permitted finding disposition, and resolve_scope for an exact proposed scope resolution. Their subjects MUST bind the applicable task inputs, policy, evidence and limits; a response never changes a required failed assertion to passed. Task-independent rule/skill revocations and policy changes use reviewed configuration releases and append-only audit records.

TaskRequest accepts optional priorityClass (incident/normal/background, default normal), incidentRef and security metadata as defined in chapter 25. POST /tasks returns a structured 403 when incident priority or security scope is unauthorized. TaskView exposes resolved priority/security, admission-derived changeClass and policy-assigned publicationTargetRefs; changeClass and publication targets are not caller input. lift_embargo decisions use EmbargoLiftSubject and the existing exact-subject response path. These additive fields are included in domain 2.0/API description 2.4.0; earlier accepted histories remain pinned.

## Design delivery API

POST /tasks accepts deliveryScope `design` for feature, refactor, performance and platform intent with a design budget class; other types, prCompletion or designSource on a design task return 422. GET /tasks/{taskId}/design-delivery returns DesignDeliveryView (the immutable DesignDeliveryRecord, its artifact ref, current DesignCurrency and linked build task IDs), or 404 design_delivery_not_started before delivery. GET /applications/{applicationId}/designs pages the application's delivered designs visible to the caller. Currency in views is an advisory projection; the authoritative check is the binding evaluated by the workflow. “Build from this design” is an ordinary POST /tasks with designSource naming the design task and delivery ref; admission rejects a mismatched work type/target or a design-scope builder with 422. Only a task in the same security group may bind an embargoed design: the build carries the design's embargoed security metadata and group (403 for a caller outside that group, 422 for a missing or different group); a non-embargoed design's build carries no security metadata. Events include design.rendered, design.delivered and design.binding_evaluated with artifact refs. These routes and fields are part of API description 2.5.0 for revision 1.13; there is no agent-writable design endpoint and no route sets a design gate.

## Review mode API profile

API description 2.5.0 on /v2 adds ReviewMode filtering to task/application lists and ReviewModeStatus on application views (effective mode, status, decision ref, expiry and audit backlog). Task/review/outcome views expose mode and separate AI approval refs. GET /applications/{applicationId}/review-mode returns the same authorized status; GET /tasks/{taskId}/ai-reviews returns immutable decisions/approval sets after the submission barrier. Pending audit selections are never exposed to agents. Mode establishment/renewal/revocation uses reviewed policy releases and the internal ReviewModeControlPlane with OperationKey, expected revision and authenticated joint human authority; there is no agent-writable mutation endpoint. Human DecisionResponse and provider-human observations reject AI provenance, including AI records hidden behind artifact refs. AI decisions enter only through trusted controller finalization of authenticated reviewer runs; they cannot set gates themselves.
