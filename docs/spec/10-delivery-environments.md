# 10 — Git delivery, deployment providers and environment lifecycle

## Delivery scopes

Report: publish a reviewed report/outcome. Patch: publish an immutable patch/source package with instructions and evidence. PR: create/update one reviewable PR per repository after current gates pass. A draft preview PR is preliminary publication only and never satisfies this scope. Preview: additionally provision and verify a bounded environment. Production: additionally satisfy merge/release authorization, controlled rollout and postdeployment observation. Design: deliver the rendered, peer-approved engineering packet without implementation (chapter 05 and below).

Scope determines completion. A PR task uses an explicit completion policy: pr_created (default) succeeds when its reviewable PR and required evidence exist; review_completed additionally requires the current-head review policy under ReviewMode to pass; merged additionally requires observed merge and integration evidence. It never waits for an unspecified merge or silently acquires merge permission. Under incident-learning/1.0, delivery of a verified fix also requires its regression test in the permanent suite or a recorded owner exception (chapter 24). A production task cannot succeed merely because a PR was opened. Documentation/research delivery never acquires deployment privileges implicitly. A design task has no PRCompletionPolicy; its fixed objective is the design PR or report described below, and it never acquires merge or deployment privileges.

A PR-scoped recipe target MAY instead satisfy delivery_complete through the accepted no-change branch in chapters 04 and 23, for any accepted PR completion mode. It MUST have an independently checked `already_compliant` or `not_applicable` RecipeOutcomeRecord bound to the pinned target revision and recipe, current required gate evidence, and reconciled absence of a candidate, task branch, PR or pending publication operation. Its OutcomeManifest has status succeeded, outcomeKind no_change_compliant or no_change_not_applicable, recipeOutcomeRef and prReviewStateRef, with empty providerHandles and no candidateRef. Any other PR-scoped task without a PR cannot succeed; needs_judgement, unknown side effects and missing evidence do not qualify.

## Design delivery

ApplicationDefinition.designDocsLocation names the repository, subpath, base branch and optional ADR index for approved designs. A greenfield design targets a draft application, which has no ApplicationDefinition and therefore no location, so greenfield designs always deliver as a report artifact (no_design_docs_location). When it is configured and eligible, the publisher controller MUST create one reviewable (draft=false) design PR per design task against that base. It commits only the rendered Markdown, and optionally an ADR index entry under the same subpath, through GitProvider with the ordinary operation identity, conditional expected-head push and reconciliation rules; no runner workspace or harness is used. Deterministic secret scanning and scope/protected-path admission apply to the rendered files; any path outside the configured subpath fails admission.

The task objective, and delivery_complete, are met when that design PR is created and read back at the expected head and base with draft=false, mirroring the narrower pr_created objective. The design task never waits for review or merge, never merges and acquires no merge authority. Merging follows the docs repository's own rules: human PR review and merge under D1, or D5 dev-only AI review/merge only when the application that owns the docs repository has its own in-force ai_only decision covering that change. AI approval of the design never confers docs merge authority. Comments on the docs PR do not reopen the completed design task; a changed design is a new design task or a later build's replan (chapter 19).

When no design-docs location is configured, delivery finalizes the rendered packet as a report artifact (reason no_design_docs_location) linked to the outcome; the objective is met when that artifact is finalized. A report MUST NOT bypass a configured eligible location except through an authorized owner_selected_report decision. If the target repository classification does not permit the packet classification (INV-28), or an embargoed task lacks a confidential target, delivery blocks with a visible reason for a resolve_scope decision and never publishes a downgraded copy. An embargoed design (TaskRequest.security.embargoed=true) follows D4: human review only and delivery only to the task's private_fork/separate_repo PublicationTarget for its security group, with provider-enforced reader checks before every push (INT-15), or a restricted confidential_report. A security-flagged design that is not embargoed follows ordinary delivery but stays in human review mode, never ai_only. DesignPrTarget records publicationMode and, for a confidential mode, the securityGroupId; its repository MUST be that PublicationTarget's publicationRepositoryId and never the ordinary design-docs repository. Both confidential forms keep the security-group label until an authorized lift_embargo decision.

The immutable DesignDeliveryRecord binds the packet, PlanReviewSubject and hash, DesignBasis (source pins, application snapshot, resolved rules, policy, accepted intent/spec version and intent/criteria digest, assurance tier and planned build delivery scope), the required ReviewMode, securityFlagged/embargoed state, each gate approval with its human or ai_panel authority, rendering digest/anchors, target, classification/embargo, ReviewMode/marker and approvedAt/approvalsExpireAt. approvalsExpireAt defaults to approval plus PolicyProfile.designApprovalTtlSeconds (90 days). The OutcomeManifest has status succeeded, outcomeKind design_approved, deliveryScope design, designDeliveryRef, the rendered and packet artifacts, the design PR handle (none for a report), the intent/plan/delivery gate evaluations, human decisions or AI approval sets and the limitation “Design only: not implemented, executed or verified; planned scenarios remain planned.” It never has a candidateRef. ai_only outcomes and design PRs carry ReviewMode and “AI-reviewed — no human review”. An unapproved or stopped design finishes incomplete as abandoned or handed_over, never design_approved. Design delivery behavior with real Git providers is **not yet proven**.

## New repository initialization

Greenfield bootstrap is a separately authorized GitProvider capability. ensureRepository and initializeEmptyRepository use stable operation keys, authoritative lookup and conditional empty-repository preconditions. A minimal approved template creates the real base commit before task worktrees. This scoped initialization may write the new default branch; subsequent business changes use ordinary candidate/PR/integration rules. Monorepo onboarding performs no initialization write. Repository retention on cancellation is explicit and independent of preview cleanup; see [chapter 17](17-project-journeys.md).

## GitProvider contract and algorithm

Operations: resolveRepository, resolveRef, ensureTaskBranch, publishCandidate, ensurePullRequest, getPullRequest, setPreviewEligibility, setPullRequestDraft, getTargetHead, prepareIntegration, enqueueOrMerge and findOperation. Each mutation uses operationId plus requestHash and expected repository/head/base where relevant.

Branch key is stable `(orgId,taskId,publicationRepositoryId)`. For ordinary work publicationRepositoryId equals the source repository; git_change.repository_id identifies the publication repository and source_repository_id preserves the source identity. PR identity is stored once; reconcile an uncertain create using the recorded provider handle or a factory marker in branch/PR metadata. Avoid broad content searches that can match an unrelated user's PR. Never overwrite human branch edits: compare expected head and route mismatch to reconciliation/review.

Reviewable publication flow: verify current candidate/gates/scope → reserve operation → reconcile any existing PR to draft → push using conditional expected-head semantics → reconcile remote branch → ensure PR or mark its exact head ready for review → read back PR base/head/draft state → persist outcome. The qualified draft-preview path below may supply the environment needed by those gates; its preliminary push does not pass them. Titles/descriptions explain intended behavior, exact candidate, relevant validation, limitations and linked child work. Candidate source cannot choose arbitrary repository/base target. For embargoed work, trusted policy assigns an isolated confidential PublicationTarget recorded on the task, with a distinct publicationRepositoryId and pinned target reference. GitCapabilities.confidentialPublication declares none, private_fork or separate_repo. Before every push (including branch initialization, rework and retries), the adapter MUST check that provider-enforced read principals are a subset of the security group, record PublicationAccessCheck and ensure the restriction remains enforced through the write. Reader enumeration includes inherited teams, installations and service principals mapped to security-group membership. Unknown principals, changed access or unenforceable confidentiality block publication and route to the security owner; nothing is pushed to the ordinary repository. Integration into the source repository requires an exact-subject human embargo lift first, followed by ordinary human PR review and gates. INT-15 qualifies the chosen mechanism.

For draft previews, trusted admission MUST first record deterministic secret-scan, scope/protected-path, classification/embargo eligibility and fork/same-repository identity checks for the immutable candidate and approved publication target. Any failed or unknown check blocks the push/label addition. Embargoed tasks MUST NOT use this pre-verification path, even with a qualified confidential target; their existing confidential publication and independently completed gates remain required. Prior plan/intent/oracle approvals remain prerequisites where applicable. The accepted plan/profile explicitly authorizes the preliminary publication capability; the trusted verification/environment controller may invoke it before the deliver node, without granting Git credentials to the author/verifier process or treating deliver as complete.

Draft-preview sequence: record admission → reserve publication operation → conditionally push candidate → ensure an open draft PR at that exact head/base → add the configured preview label → bind the immutable EnvironmentPlan and CI release manifest → reconcile exact head SHA and running image digests/readiness → independently verify that composition → pass all current candidate gates → setPullRequestDraft(draft=false) with the current gateSetRef → read back exact head/base and draft=false. A draft is preview-only, not reviewable; it cannot satisfy pr_created, review_completed, review_passed, delivery_complete or merge authorization merely by existing. Verification records head and digest inventory before and after checks. A failed/inconclusive check leaves the PR draft. Ready-for-review requires all applicable pre-delivery candidate gates (including independent outcome, skeptical review and integration checks); PR-completion/merge gates under ReviewMode follow ready-for-review and are not prerequisites for creating the preview. Admission and final gate evidence are separate immutable artifacts passed as publicationEvidenceRef; an admission record is never a gateSetRef.

PullRequest observations expose draft, labels and distinct baseRepository/headRepository identities (provider, installation and immutable external repository ID); repositoryId identifies the registered base. A null/unobservable headRepository fails preview admission. For this profile, PRHeadObservation.draft MUST be present on review read-back; an absent/unknown value cannot establish reviewable publication or PR completion. Persist PRReviewState.phase=preview_only with the current candidate/head while preparing or reworking its preview. getPullRequest reads eligibility; setPreviewEligibility changes only the operator-configured preview label, idempotently preserving all unrelated labels. Label additions require admissionRef and matching current head/base repository identities; removals require a retirementRef and admission fence. ensurePullRequest binds expectedHead/expectedBase and explicit draft state; it cannot silently promote an existing draft. setPullRequestDraft(draft=false) requires exact-head/base gate evidence; draft=true records authorized rework/invalidation reasonRef and may fence a revision even when its admission checks fail. Each mutation binds OperationKey/requestHash, PR identity and head expectations, reads provider state before and after, and reconciles uncertain outcomes through findOperation. A changed head conflicts; do not retry with changed inputs under the old operation ID. Provider label/draft APIs need not offer atomic head conditions: controller serialization, admission fencing and independent review/merge checks MUST prevent a raced mutation from authorizing a different revision. Reconcile any raced ready state back to draft and supersede its evidence. Git write credentials for draft/label mutations MUST be scoped separately from the generator read credential; record identities/grants/rotation ownership, never values.

Merge flow: validate current merge authority (D1 human-reviewed policy or D5 dev-only authority); production additionally requires human release_authorized → build integration candidate against current target → run required integration gates → queue/merge with expected revisions → observe actual merged commit → bind source/artifact provenance. If provider merge behavior cannot enforce the tested composition, the adapter must use a safer controlled strategy or declare merge unsupported. Release qualification includes squash/rebase/merge-queue scenarios.

The trusted runner/checkpoint step writes authorship trailers (task, stage run, behavior release, recipe) from server records when creating every factory commit, before freezing its ID. The Git adapter MUST validate those trailers against server records before publishCandidate and MUST NOT rewrite the frozen commit; it refuses missing/mismatched trailers or a candidate that has not passed secret scanning. See [chapter 25](25-data-security-operational-safeguards.md).

## DeploymentProvider contract

Required methods for automated preview: describeCapabilities, submit(plan,operationId), findByOperationId, getStatus(handle), destroy(handle,operationId). The provider returns stable resource identity and an operation status distinct from environment readiness. Optional methods include snapshot, restore, extendLease, promote and rollback; the observed release is reported through getStatus(handle).observedReleaseRef.

Capability declarations include idempotentSubmit, operationLookup, authoritativeNotFound, cancellation, cleanup, readiness, deploymentInventory, snapshot, restore, promote, rollback, isolatedData, networkModes and hermetic. Omitted optional capabilities mean unsupported. cancellation means destroy(ctx, key, handle) on a pending submission aborts it without orphaning resources. Each declaration is backed by conformance evidence and adapter version. Missing idempotency/lookup is a material limitation: an uncertain submission enters needs_operator and cannot be automatically resubmitted.

### Argo CD branch-preview provider

ADR-32 selects ApplicationSet's GitHub Pull Request generator as the reference Kubernetes preview provider; W-041 remains an equal MCP alternative behind DeploymentProvider. The organization already uses Argo CD after merge to `dev`. This adapter MUST use a separate preview ApplicationSet, AppProject and target permissions; the existing Argo configuration and production release path MUST remain unchanged. D5 may authorize the factory to merge only into the configured dev/integration branch that this existing path deploys; it grants no Argo or production promotion authority. W-139/W-140 and INT-17 define implementation and qualification; this provider is **not yet proven** against a real cluster.

An operator-owned ApplicationSet MUST discover eligible open PRs and generate one Application and isolated namespace per repository/PR, with stable names across commits. Its source is the approved app repository/chart or manifest path at `targetRevision: '{{.head_sha}}'`. Eligibility requires the configured opt-in PR label: factory task PRs receive it automatically after exact-candidate admission and draft publication (or fully gated reviewable publication); humans MAY add it to their PRs. Unlabelled PRs get no preview. Closing, merging or losing eligibility MUST remove the Application on reconciliation. The generator supports label selection, head SHA templating and reconciliation-driven removal. [Argo PR generator](https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators-Pull-Request/)

Fork PRs MUST NOT receive previews, even if labelled: deploying their untrusted code would expose cluster access and preview secrets. Before any generated Application can sync, trusted adapter/admission MUST check GitHub head-repository identity against the approved base repository, current head, task confidentiality and capacity. A label filter alone is insufficient. The same fail-closed checks MUST cover human labels and direct generator reconciliation, including retries; no transient forbidden workload may start. ApplicationSet templates, AppProject, destinations and security policy MUST remain operator-controlled, not PR-controlled.

Authenticated PR webhooks to the ApplicationSet webhook endpoint SHOULD trigger reconciliation; polling MUST remain the fallback. Configure `requeueAfterSeconds` explicitly (reference target: 60 seconds, subject to GitHub limits); the documented default is 30 minutes. Without a delivered webhook, creation, update and deletion can lag by one polling interval plus controller/API backlog and sync/prune time. Neither webhook delivery nor polling gives an instantaneous or hard completion bound; record actual lag and qualify timeout/cleanup objectives. [Webhook and polling semantics](https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators-Pull-Request/#webhook-configuration)

The branch-preview profile MUST require EnvironmentPlan.pullRequestRevision and releaseManifestRef, cross-checked against candidateRef and every deployable. `submit()` has a bounded wait; timeout preserves the operation/handle for lookup and status reconciliation, never a success or a fresh submission. A head change during submission supersedes that operation. The adapter MUST read actual status rather than desired `spec.source.targetRevision` alone. Map Argo OutOfSync or a running sync to pending/provisioning (or deployed if resources exist); Synced with progressing health or incomplete probes/hooks is pending/deployed. Only exact Synced + Healthy + completed readiness and digest checks is succeeded/ready. Failed/error sync or terminal unhealthy/probe/hook failure is failed with diagnostics; unavailable/Unknown status is unknown. A revision/digest mismatch blocks candidate success and reconciliation continues. Readiness is not behavior: only independent verification can establish verified delivery.

CI MUST build images from the PR head commit, record provenance and the candidate's release manifest, and deploy immutable digests. If the template passes the SHA as an image tag, the registry MUST enforce immutable tags; the adapter MUST verify actual running image digests against every image in that manifest, including init/migration workloads, with explicit platform-digest resolution for multi-architecture images. `imageDigestVerification=unknown` or mismatch cannot pass. A preview at another sync revision or digest is not evidence for this candidate, even if Healthy. Each new PR commit redeploys in place only after admission: return the PR to draft/preview_only, advance the durable current-plan generation, record its observed revision, supersede older results and rerun verification. If revision/inventory changes during a check, invalidate that check. Baseline/candidate comparisons requiring simultaneous or reset environments need a separately qualified profile; in-place PR previews do not imply snapshot/restore support.

Each preview namespace MUST have default-deny ingress/egress NetworkPolicy with explicit permitted egress, ResourceQuota, LimitRange and chapter 09 Pod Security/admission controls. Ownership labels MUST bind task, operation, repository, PR, head SHA and expiry; use safe encoded label values plus full annotations, including application/team and managed-by identity for admission/sweeping (chapter 11). Human PRs MUST receive a durable preview-only tracking task/owner record supplying the existing taskId and operation ledger bindings; this starts no authoring run and asserts no factory-authored change or task-verification result. Secrets MUST be scoped through an external secrets mechanism, never production credentials. Each preview MUST get an operator-managed database cluster (for example CloudNativePG), or its own database and credentials on a shared non-production server with cross-database access denied. No fallback to shared dev or production data is allowed. Migrations and versioned seed fixtures MUST run as a sync-hook Job, ordered after database readiness and before application readiness; retries MUST be idempotent, failures block readiness, and evidence records fixture/classification and migration revisions. INV-28 applies to all loaded data.

Applications MUST carry `resources-finalizer.argocd.argoproj.io`, with resource preservation disabled and controller policy permitting update/delete, so Application deletion prunes resources. Argo does not delete namespaces created only by `CreateNamespace=true`: the namespace MUST be an owned manifest or be removed by the factory sweeper using its ownership labels. Deletion MUST also inventory PVCs, backing volumes, external databases/credentials and hook resources; a vanished Application alone proves nothing about complete cleanup. Routing MUST use `<slug>.<preview-domain>` with collision-safe repository/PR slugs, wildcard DNS and a wildcard certificate (for example cert-manager). Access MUST be restricted to authenticated, authorized reviewers; previews are never publicly exposed by default. Embargoed security tasks (D4/INT-15) MUST be refused on shared-cluster previews unless an isolated, qualified confidential target exists, including restricted URL, logs and evidence access. Record scoped PR-generator GitHub token and CI image-build credential identities, grants, secret references and rotation ownership; never their values in plans/logs (chapters 09 and 25).

A maximum lifetime (default 24 hours) and explicit idle expiry (reference default 4 hours since authorized reviewer activity or a new admitted head) MUST backstop PR-close deletion. Polling/probes MUST NOT renew idle time. Extensions require policy authorization within a finite profile maximum. The existing sweeper MUST reconcile expired/orphaned resources by ownership labels, revoke eligibility first and prevent recreation while retiring. Adapter/admission MUST atomically enforce concurrent preview caps per application and per team, including human PRs, pending admissions and retiring/unknown resources. The generator itself has no such cap; excess requests MUST queue with a visible queueReason and no workload, then recheck eligibility/current head when capacity is available. INT-17 closes the selected limits and platform mechanisms.

### Current-plan and public status projection

An EnvironmentHandle and environment row remain stable across admitted heads. generation starts at 1; plan_ref is the current immutable plan, and current_operation_id binds its submission. Before admitting a new head, the controller fences sync/verification and reviewable publication, rechecks eligibility, and reserves a new external_operation whose immutable request_ref records environment ID, new generation/plan/head/release manifest, previous generation/plan/operation and admission evidence. In one serialized compare-and-set transaction on the expected revision/generation/plan, update plan_ref and current_operation_id, increment generation and revision, set state=planned, and clear endpoints, observed_release_ref, verification_ref, deployment_status and status_observed_at. Supersede dependent gates/review results in the same admission transition. The reference SQL grants these columns to factory_runtime and guards the generation transition; the trusted controller additionally validates immutable request contents and authorization. A stale concurrent transition fails and reloads; retiring/retired resources cannot advance. Retry of the same admitted operation attaches without another increment. Initial creation records generation 1 and its operation together. Old plans, operation requests, observations and verification artifacts remain immutable and reachable through operation history; never create a second row for the same external handle or relabel old evidence as current.

GET /environments and GET /environments/{environmentId} project planRef, generation and currentOperationId from that committed row. Persist each provider observation as an immutable operation result artifact with an append-only task_event/artifact_link retaining its operation/generation binding, then atomically project sanitized DeploymentStatus into deployment_status/status_observed_at and increment revision only when the expected generation/operation/plan still matches. Late observations from old operations remain historical and cannot overwrite current status or verification. EnvironmentView.status/statusObservedAt expose queueReason, observedRevision, imageDigestVerification and permitted previewUrl/endpoints; absence of an observation means unknown, never success. Queued rows persist a pending/provisioning status with a safe queueReason before returning the response, so polling/listing after restart still explains the wait. Remove queueReason once admitted; do not retain a stale queue explanation. Restrict both routes by task/application and embargo access, strip credentials, secret values and other tenants' capacity/identity details, and authorize diagnostic/artifact links separately. Use a generic policy-safe reason when details are restricted. Status is an observation, not a gate verdict; only current exact-head/digest verification can advance delivery. See the generated queued-environment.json and queued-environments.json fixtures.

## EnvironmentPlan resolution

Inputs: application/profile definitions, candidate/release manifest, purpose, dependency mode and lifetime. Resolve each deployable to immutable image/source artifacts, template/recipe revisions, configuration hashes and secret references. Choose dependencies as deploy, snapshot, sandbox, stub or existing read-only; record why the mode is valid for the intended check.

Map databases/queues/buckets into isolated names and least-privilege credentials. Apply schema migrations, seed versioned fixtures, and record initialized state. Define dependency startup/readiness order; cycles require explicit staged bootstrapping/readiness rules. An environment cannot silently fall back to production data or a shared mutable dependency when isolation fails.

## State machine

| State | Entry action and transition |
| --- | --- |
| planned | Persist resolved immutable plan; validate quota/capabilities. |
| provisioning | Submit once with stable operationId; poll/reconcile actual result. |
| reconciling | Unknown submission/status; perform bounded lookup until known or needs_operator. |
| deployed | Provider reports resources created; not yet application-ready. |
| preparing | Apply declared migrations/fixtures and readiness checks. |
| ready | Dependencies and application health established; schedule work-specific checks. |
| verifying | Execute acceptance/regression/benchmark/rehearsal against exact composition. |
| verified / verification_failed | Persist trusted result and observed release IDs. |
| retained | Available for authorized review until expiry. |
| retiring | Request deletion and reconcile all owned resources. |
| retired | Provider confirms deletion or retained resources have a separate owner/lifetime. |
| needs_operator | Unrecoverable/unknown state with explicit resource and next action; sweeper continues permitted reconciliation. |

Readiness and behavior are separate gates. Service health endpoints returning 200 do not prove the feature works. For environment-only bugs, baseline and candidate use equivalent plans/fixtures with the intended source difference; mutable baseline state is not reused accidentally.

## Idempotent external operation ledger

Before a mutation, persist `(operationId, provider, kind, requestHash)` and a request_ref to an immutable request artifact containing desiredState, and lock its logical key. If the same operation already succeeded, return the saved outcome after any required freshness read. Same ID/different hash is a conflict.

After a request timeout: query by operationId. If found, attach and continue. If the provider authoritatively proves no operation/resource was created, a retry may use the same ID. A transient 404/eventual-consistency gap is not sufficient proof. If lookup is unavailable, record unknown and ask an operator to resolve; a local lock alone cannot eliminate remote duplicates after a crash.

Default reconcile window 30 minutes, exponential polling 5–60 seconds with jitter; after that, needs_operator with resource ownership preserved. Cleanup runs even if the task was cancelled. Persistent environment expiry is enforced by both EnvironmentWorkflow and independent sweeper, so one failed workflow cannot create an indefinite leak.

## Production release policy

Production is disabled per application until its profile has qualified readiness, observed-release inventory, defined rollback/roll-forward and ownership. Require current integration evidence, artifact digest, target environment, expected current release, migration plan and configured authorized decision. No user is asked to approve an unspecified future candidate.

Reference rollout: deploy to a canary cohort if provider supports it, run smoke/contract checks, observe predeclared error/latency/saturation indicators for a profile-defined window, then promote. If no canary capability exists, explicitly choose a supported rollout profile; do not pretend a generic MCP deploy offers it. Metrics thresholds and duration are app-owned profile fields established during onboarding, not guessed by the authoring model after deployment.

On failure: stop promotion, reconcile actual state, execute the preauthorized safe mitigation, verify recovery and record the failed release. Data migrations may need roll-forward or restored backup; automatic rollback is allowed only when its applicability was established. Cancellation during release means reconcile and apply the configured safe stop, not blindly delete production resources.

## Several services

ReleaseManifest lists every service's source and image digest, contracts, schema compatibility and order. Parent workflow reserves one environment/release composition. Children cannot independently update a shared dependency during integrated verification. Backward-compatible expand/migrate/contract sequencing is preferred for data/API changes; irreversible coordinated releases require application-specific review and rehearsed recovery.

## Cleanup and evidence

Record deploy logs, provider request/result digests, endpoints, observed version inventory, readiness and verification reports, fixture provenance, resource ownership and deletion confirmation. Endpoint links may expire; evidence references remain durable. Default preview lifetime is 24 hours. Extension requires an authorized reason and resource quota, and cannot postpone cleanup indefinitely without transferring ownership.

## AI-reviewed merge to dev

A pre_repository decision MUST have an effective ReviewModeRepositoryBinding before PR review or merge. The merge controller resolves its bootstrap receipt and organization policy, verifies the exact decision/application/repository/branch/identity and live protection, and fences the effect under the same application authority revision. A missing or mismatched binding refuses merge.

Publication/export validation resolves every human-review reference in the output itself, including decisionRefs and voluntaryHumanReviewRefs and nested human approval sets, in both review modes. Unknown, cyclic, mismatched or AI-backed human references reject. An ai_only output carries reviewSubjectRef and its task identity; AIReviewSubject binds the gate and, for PR review, repositoryId, pullRequestId, baseBranch, expectedHead and expectedBase. The output must match these exact fields. Every AI-authority publication revalidates the full panel and reviewer qualifications even when a preliminary open draft carries no approval-set refs; completed outcomes and merges require the approval set. A merge requires a pr_review panel and the configured dev branch. Every retained PR vote must be at or after the repository binding became effective, as well as within the decision's validity and no later than evaluation.

Under an in-force ai_only decision and an explicitly accepted merged completion objective, the factory MUST require unanimous exact-head AI panel approval, all required checks and qualified preview verification at the exact head SHA, current EnvironmentPlan generation and running image digests before merging. Recheck the tested integration composition and moving base through the ordinary merge protocol. The only target is the application’s configured dev/integration branch used by the existing merge-to-dev Argo CD path; branch previews use ADR-32 or the equally qualified MCP alternative. INT-18 MUST record the exact repository/branch and provider-enforced allowance for the factory’s own scoped GitProvider identity on that branch only. Missing or unverifiable protection/identity facts refuse merge.
