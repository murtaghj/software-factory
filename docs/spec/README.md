# Software factory — implementation specification

Revision 1.13 · 29 October 2026

This package specifies the service discussed in the architecture guide: a vendor-neutral engineering factory coordinated by Temporal, executed on Kubernetes, and connected to established coding harnesses, Git, application knowledge, verification and pluggable deployment providers.

The requirements and defaults here are concrete design proposals for implementation. They do not describe an already deployed system. Organization-specific integrations are isolated in the decision register; their missing values do not imply that a generic adapter has already been proved against the actual provider.

## Read and build

1. Read [scope and architecture](01-scope-architecture.md) for ownership, boundaries and invariants.
2. Implement [data](02-domain-data.md), [APIs](03-api-events.md) and [Temporal](04-temporal.md) together. They define three different kinds of state: records, requests and workflow decisions.
3. Read [complete engineering plans and peer sign-off](19-peer-plan-review.md), [the three project journeys](17-project-journeys.md), [the required greenfield interview](18-intent-interview.md) and [workflows and gates](05-workflows-gates.md): greenfield, existing-project features and bug repairs use distinct versioned templates over shared components.
4. Build the [runner](06-runner-workspaces.md), [harness/context layer](07-harness-context.md), [registry](08-registry-knowledge.md) with its [sources, onboarding, readiness, recipes and campaigns](23-readiness-recipes-campaigns.md) [context gathering and incident learning](24-context-gathering-incident-learning.md), [data governance and safeguards](25-data-security-operational-safeguards.md) and [investigation discipline](26-investigation-discipline.md), [verification](09-verification-security.md) and [delivery](10-delivery-environments.md) behind the defined interfaces.
5. Apply [rules, role content and admitted skills](21-rules-role-content-skills.md), [reference practice and adoption decisions](22-reference-practice-adoption.md), the [platform and operations](11-platform-operations.md) and [UI/access](12-ui-access.md) requirements from the first usable slice.
6. Execute the [acceptance programme](13-testing-release.md) and [sequenced backlog](14-build-backlog.md). Close each [decision register](15-decisions-sources.md) entry at its listed gate.

The [plan review concept](../plan-review.html) demonstrates the layered engineering review using a fictional complete packet; its decisions are local demo state only. The generated [HTML reader](../implementation-plan.html) contains the complete written specification. The original [architecture guide](../index.html) remains the shorter interactive explanation.

## Conventions and precedence

- **MUST** means required for the described release. **SHOULD** means the default with a documented reason required for an exception. **MAY** denotes an optional capability.
- JSON Schema defines serialization; the SQL schema defines storage constraints; workflow tables define progression; interfaces define provider boundaries. A contradiction is a specification defect to fix before implementation, not a choice for individual components.
- Examples contain fictitious identities and digest values. Deployment templates and protocol fragments are design material, not working credentials or verified organization integrations.
- Status projections can lag; the workflow is authoritative for progression. Provider resources remain authoritative for whether an external side effect actually happened.
- Each implementation PR references its backlog ID, affected invariant IDs and acceptance IDs. Changes to these documents and contracts are reviewed with the implementing code.
- Keep this package in the service repository under `docs/spec/`; generated HTML is a reading view. Use a changelog and ADR for changes to invariants or storage/contract compatibility.

## Definition of ready to implement

The plan supplies the target behavior, ownership, interfaces, failure handling, work breakdown and validation obligations. M0 closes access and provider choices, pins dependencies and validates the reference contracts with the selected toolchain. Do not label a vendor capability supported until its conformance test passes. At least one real deployment provider must pass conformance before preview delivery is enabled; every enabled provider must qualify independently.

## Definition of delivered

The service supports greenfield development (new repository and new component in a monorepo), existing-project features and bug repairs across all eight specified work types, plus design-only delivery and builds from current approved designs; two harnesses pass portable-handoff conformance; the selected Git and deployment providers pass side-effect reconciliation tests; the recovery and isolation suite passes; operations can restore the system from backup; and every released outcome can be traced to its exact source/artifact, policy, evidence and delivery decision. Hermetic execution is an explicitly later capability, with its integration contract defined now.
