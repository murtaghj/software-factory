# 02 — Domain, persistence and artifact formats

## Identity and version rules

Use UUIDs generated outside workflow code for external records. Logical stageRunId is deterministic from task ID, plan version, node ID and semantic attempt; store the components and a unique constraint, not only a concatenated string. Current wire fields named stageRunId or *StageRunId carry `stage_run.logical_id` in the canonical form `task-<taskId>/plan-<planVersion>/<nodeId>/attempt-<semanticAttempt>`. Persistence MUST resolve it to the surrogate `stage_run.id` (uuid) through `UNIQUE(org_id,logical_id)` before writing FK columns; that uuid is never exposed on the wire. Retained factory tools 1.0.0/1.1.0 use their frozen readers and preserve historical string stage IDs; they MUST NOT be revalidated against the current LogicalStageRunId pattern. Temporal Run ID is diagnostic and never part of an external idempotency key. Repository identity is provider installation plus immutable repository ID, not a mutable URL.

Every owned row has `org_id`; every owned reference includes that organization in its foreign key. All timestamps are UTC `timestamptz`. Store monetary amounts as integer micro-USD plus price-card revision; store observed usage separately from estimates. Commit IDs are full, nonzero 40- or 64-character lowercase hexadecimal object IDs with repository identity; SQL enforces the same format through `git_object_id`. SHA-256 artifact digests are 64 lowercase hexadecimal characters. Lists whose order has no meaning are sorted before canonical hashing; use RFC 8785-compatible JSON canonicalization in the implementation.

Domain envelope examples use `2.0`; the REST contract is /v2. Workflow templates use independent semantic versions: greenfield is now 4.0.0 and the other supplied templates are 3.0.0. Revision 1.4 adds optional wire fields to existing 2.0 envelopes; the new templates and pilot qualification profile require their applicable structure-outline, PR-completion, factory-tool and evidence fields. Legacy templates keep their original readers and semantics; do not silently supply new behavior to running histories. Breaking formats create a new major revision. Readers must reject unknown major versions and unrecognized fields in security-sensitive envelopes. Migration tools produce a new artifact and preserve the original.

## Target context and bootstrap persistence

TaskRequest.targetContext is a strict tagged union. Its primary applicationId must appear in applicationIds, with every affected ID authorized. New targets pin a draft revision/ref; RepositoryIntent may be unresolved during the interview but is mandatory in the accepted BootstrapPlan; existing targets require a registered definition. Resolve a compatible WorkflowTemplateRef and persist it in ExecutionPlan. InputBinding includes its definitionRef, plus bootstrapPlanRef/foundationRef when relevant. Missing or mismatched references fail admission.

The application row starts with lifecycle draft and no current definition. Immutable application_draft_version records live in the artifact store before there is Git source. application_bootstrap owns the active claim, request hash and operation identities. A partial unique index prevents concurrent unresolved onboarding tasks. ready/cancelled/failed release the claim only after known effects and ownership are recorded; uncertainty remains needs_operator. Template identity on workflow_binding is a projection of the accepted plan, separate from worker build identity.

ApplicationSnapshot can contain draft refs for greenfield foundation work and registered dependency definitions. After accepted foundation publication, capture a new snapshot/plan for the slice and children; retain original artifacts and reevaluate affected gates. Reference SQL is for fresh installation; existing implementations require an audited backfill and versioned migration as described in [chapter 17](17-project-journeys.md).

## Ownership and consistency

Database row edits do not drive Temporal progression. Workflow transition records are projected through `projectTransition(taskId, sequence, state, refs)`. The repository MUST lock the task row and compute the canonical SHA-256 hash of `(sequence, state, refs)`. A higher sequence applies the transition and stores `projection_sequence` and `projection_hash` together; an equal sequence returns idempotently only when the stored hash matches, otherwise it raises an integrity incident. A lower sequence is rejected as stale. The sequence persists across workflow runs; a zero projection sequence has no hash.

Workflow projection sequence and dashboard event sequence are distinct. `projection_sequence` orders workflow state changes; `last_event_sequence` allocates every task event, including runner progress. Lock the task row, increment the event counter, insert the event and update the relevant projection in the same transaction. Deduplicate by producer event ID first. A runner progress event cannot advance the workflow projection counter. A task snapshot exposes both counters for gap-free stream resumption.

Task creation MUST set `owner_principal_id` to the creator; the reference trigger supplies this default when the field is omitted. `reassign_owner` changes the accountable owner through an audited command. `take_over` sets `interactive_holder_principal_id` to the authenticated human only after checkpoint/epoch transfer; `hand_back` clears it after transfer to a new automation epoch. These commands MUST update the task projection and append a bound task event atomically; the holder is separate from the accountable owner.

Use transactions for task+launch, command+dispatch, operation reservation, workspace epoch claim, budget reservations and projection+task event. Long network calls occur outside transactions. Claim work with row locks and bounded leases; release the transaction before network I/O. PostgreSQL documents `SKIP LOCKED` for avoiding contention in queue-like consumers; its intentionally incomplete view must not be used for correctness-critical general reads. [PostgreSQL SELECT](https://www.postgresql.org/docs/18/sql-select.html)

For budget admission, lock the parent and child budget accounts in a stable root-to-leaf order, reconcile the unique reservation key, and require charged plus outstanding reservations plus requested allowance to fit every applicable limit before inserting the ledger entry. Late actual charges may exceed estimates; record them truthfully and stop new admissions. For capacity admission, take a transaction-scoped advisory lock for each sorted organization/provider pool key, count active/reserved slots and insert the reservation atomically. Expired reservations are reclaimed only after their execution allocation is reconciled; wall-clock expiry alone cannot free a still-running workload's capacity.

The workflow records decisions in history; the database is the query and operation ledger. A DB outage can pause progress even while a process runs. A runner may retain buffered logs locally within its limit, but cannot acknowledge a durable checkpoint or terminal result until persistence succeeds.

## Artifact storage protocol

A source's organization-defined DataClassification is separate from the artifact access class (`ordinary`/`restricted`/`sensitive_session`). The shared word `restricted` implies no mapping between these policies.

1. Authorize the authenticated producer and reserve an upload ID bound to organization, reservation scope, authority ref, media type, schema version, classification and maximum bytes. Stage producers MUST use task_stage with an exact task/stage binding; resolve the logical stage ID and verify it belongs to that task. Only trusted registry/operator controllers MAY use reserveOwned: application_draft binds an application identity reserved before its first draft artifact, and organization_controller binds the emergency_stop or policy_release controller. Both owner scopes MUST have null task/stage IDs. The service MUST verify current application-creation/owner grants or organization-controller authority from authenticated context and pinned policy; a caller-supplied owner or authorityRef alone grants nothing. Persist that authorization and derive data classification/embargo labels before issuing the bounded upload capability. Stage workloads MUST NOT obtain owner-scope capabilities.
2. Upload to a temporary key using bounded multipart upload if needed. Credentials can write only that upload prefix.
3. A trusted artifact service streams/verifies length and SHA-256, checks schema/media type and applies redaction/classification policy. Finalization MUST reject a caller whose authenticated producer or task/stage/owner scope differs from the reservation, whose current owner authority has been revoked, or content whose media type, schema version or classification differs from the reserved values.
4. Promote to immutable `org/{orgId}/sha256/{digest}` or equivalent conditional-write key. Keep object version metadata and verify existing content if already present.
5. Insert finalized metadata and provenance, then return ArtifactRef. Existence without finalization cannot satisfy a gate.
6. Sweep incomplete uploads after 24 hours. A failed DB commit after object upload leaves an unreferenced object for reconciliation; it does not justify returning a reference.

A digest already present reuses the verified object; the artifact service returns an existing artifact row only when mediaType, schemaVersion and classification match, otherwise it registers a new row for the same object. A returned ArtifactRef MUST carry the metadata validated for that registration; ArtifactView.mediaType/sizeBytes MUST match its ref. New producers retain provenance through the registration audit, owner-scope reservation and any task links even when the artifact row is reused. Retention reachability is computed per object across all artifact rows and links; re-registration can extend but MUST NOT shorten retention. Object access always authorizes the specific artifact registration and its caller-visible links.

ArtifactRef includes `artifactId`, `sha256`, `mediaType`, `schemaVersion` and `sizeBytes`. Storage credentials/URLs stay out of workflow histories. Downloads go through an authorized resolver issuing a short-lived URL or streaming data. Do not deduplicate readable metadata across organizations.

## Retention defaults

Use configurable organization policy. Initial proposals: failed/debug workspace 24 hours; completed workspace 2 hours after checkpoint acceptance; previews 24 hours with one authorized extension up to 7 days; raw transcripts 30 days; ordinary execution logs 90 days; accepted source, gate evidence and audit records 365 days minimum. An active task, decision, release or legal retention flag pins referenced artifacts. Secrets are never retained as artifact content.

Deletion is a two-pass mark-and-sweep with a seven-day grace window: compute retained roots, mark eligible unreferenced objects, recheck reachability and then delete. Versioned object-store retention/legal holds must be respected. Missing objects produce `artifact_unavailable`, never silent regeneration under an existing digest. Backup retention is coordinated with source/object references.

## Query design and migrations

Index organization+status+updated time on tasks, task+node+attempt on runs, task+sequence on events, provider+kind+logical key on operations (the uniqueness constraint), workspace+epoch on allocations, cleanup state+expiry on environments, and GIN full-text vectors on approved knowledge. Paginate the task list with stable descending `(created_at,id)` cursors backed by `task_list_cursor_idx`; other lists MUST define a stable cursor and matching index in their implementation migrations. Cap list sizes at 100.

Use expand/backfill/contract migrations. New workers read both supported contract revisions during rollout; background backfills are restartable and measured. Never change a field's meaning in place. Initial implementation must run schema installation, tenant isolation, uniqueness, migration-forward and backup-restore tests in PostgreSQL 18. The supplied DDL is a reference, not evidence these tests have run. Runtime grants MUST limit updates to named projection/status columns; tenant/record identities, digests, authenticated actors and evidence remain immutable. Organization provisioning belongs to migration/admin credentials; runtime has only an intentionally unscoped ID/status lookup. W-108 and W-128 MUST qualify the revised grants and tool-call lifecycle in PostgreSQL; until then this revision is not yet proven by runtime privilege tests.

## Factory tools, review follow-through and application health

The 1.4 profile adds four reference tables. factory_tool_call stores the allocation-bound request digest, server-derived role/input binding, sequence, receipt state and durable result refs; unique call IDs deduplicate retries and a partial unique index on proposal_accepted permits one schema-valid accepted submission per semantic stage run. Invalid submissions are logged with proposal_accepted false and cannot consume that slot; the flag never clears after acceptance, including finalisation failure. An identical later call links the original receipt rather than creating a second accepted proposal. A proposal is not an accepted StageResult. Tool call artifacts and final receipts remain linked to the task retention roots.

pr_review_state projects each task/repository PR's immutable completion policy, expected head, review-round count, provider cursor/observation and workflow state ref. Rows are per-PR projections of one task-level PRReviewState revision. Every row for a task MUST carry the same revision, completion_mode, phase, review_round, review_deadline and state_ref, written in one transaction when that revision is committed; expected_head, observed_head, provider, external_id and provider_observation_ref are repository-specific. GET /tasks/{taskId}/pr-review renders the PRReviewState at state_ref for the highest committed revision. The workflow owns progression; the provider owns actual PR state.

For a no-change recipe completion there is no per-PR row. The immutable completed_no_change PRReviewState is retained through WorkflowCheckpoint.prReviewStateRef and OutcomeManifest.prReviewStateRef; TaskView.prReview and the same read endpoint return that state without inventing a provider handle or PR. RecipeOutcomeRecord and its evidence are task retention roots.

application_health_sample is append-only evidence keyed by application, cohort, measurement window and metric version; samples include denominators, source refs, attribution uncertainty and maturity. autonomy_policy_decision is an append-only authorized policy revision with ledger evidence and scope. application_health.measured denotes insertion of a health sample exposed by the application-scoped health read endpoint, not a task_event. policy.tightened records an autonomy_policy_decision plus an audit_event; it also appends a task_event with the decision ref to each nonterminal task in the affected cohort whose admission or publication it holds (chapter 22). No coding-pod identity can write these tables.

WorkflowCheckpoint carries prReviewStateRef and pending human-decision refs; tool receipts survive separately in the durable operation records. InputBinding pins behaviorReleaseRef, resolvedGatePolicyRef, factoryToolSetRef and reviewPacketRef where applicable. A BehaviorRelease binds adapter, model-family/profile, prompt/instruction/skill package, tool schemas, evaluators and tier-policy revisions with qualification evidence. Reviewer family and selected mode are recorded with the review; different families reduce one source of correlation but do not prove independence.

Public request prCompletion is valid only for deliveryScope pr; the accepted spec persists an explicit default of pr_created. Production uses its existing release completion rules and cannot substitute a PR-only outcome. OutcomeManifest distinguishes delivered, verified_fix, fix_proposed_unreproduced, design_approved, abandoned and handed_over; design_approved is valid only for design scope and never carries a candidate; status still records succeeded/incomplete/failed/cancelled independently. A proposed unreproduced fix is always incomplete against the original bug objective.

Task admission metadata (revision 1.11): priorityClass defaults to normal; incident requires authorized intake. Optional security is restricted to bug/maintenance, eligible design-scope tasks and (embargoed only) builds that inherit the group of the embargoed design they name, and requires a securityGroupId when embargoed; incidentRef links the incident evidence. Admission resolves changeClass from the pinned recipe, otherwise from the trusted work-type/path classifier (falling back to workType); a caller cannot select it. The task projection persists this value and TaskView reports it. Policy-assigned publication targets are retained in git_change.publication_target_ref and exposed by TaskView.publicationTargetRefs; repository_id identifies the publication target and source_repository_id identifies the ordinary source. Readiness uses this exact class and pinned snapshot. ProviderEligibilityBinding pins the effective classification and policy in StageInput/InputBinding and the allocation; the server verifies that the inline StageInput binding equals its immutable input reference.

Security-group membership is authoritative identity data, maintained outside factory_runtime. Authenticated transactions set factory.org_id and factory.principal_id; workload principals need explicit security-group membership. Restrictive RLS covers task rows and their direct/indirect projections, artifact metadata, logs, knowledge and auxiliary envelopes. Trusted repositories inherit embargo labels before insertion, including child/follow-up tasks, cached matches and exported/logged summaries; group-aware artifact deduplication never shares an unrestricted row. Embargo lift requires the exact authorized human decision and cannot silently relabel old artifacts. W-137 qualifies these boundaries and forward migrations; reference DDL is not yet proven.

## AI review policy and provenance

ReviewModeDecision and ReviewModeTransition persist application-scoped, revisioned authority and automatic tightening; AIReviewDecision/AIReviewApprovalSet persist exact-subject AI provenance separately from human decision/PlanApprovalSet/IntentApprovalSet rows and refs. The control-plane-only ReviewAuditSelection is chosen before execution and retained across retries; ReviewAuditResult is separate append-only human evidence. Tenant-qualified foreign keys, forced RLS and column-limited grants follow the existing pattern. AI identities cannot be written to human decision fields. Current projections may change mode while historical outcomes preserve their mode/marker and voluntary human review separately. See ai-review/1.0 contracts and chapter 11 for service predicates beyond SQL/JSON shape checks.

## Design delivery records

design-delivery/1.0 adds DeliveryScope `design`, OutcomeKind `design_approved`, the render_design stage kind, five design template IDs, Budget.budgetClass, PolicyProfile.designBudget/designApprovalTtlSeconds, ApplicationDefinition.designDocsLocation, PlanReviewPacket.plannedBuildDeliveryScope, TaskRequest.designSource and designBuildBindingRef/designProfile on InputBinding and ExecutionPlan. DesignDeliveryRecord and DesignBuildBinding are immutable artifacts projected into design_delivery and design_build_binding. budget_account.budget_class separates design spend: it must equal design exactly when the task's delivery scope is design (composite key to task, cascading pr/preview changes), and a parent account must have the same class. task.design_source_task_id records a build's design; a guard requires the same work type, application, target context and security group as the design. task.delivery_scope is checked against eligible work types and a trigger forbids toggling design; design_delivery references task (org_id,id,delivery_scope) so only design-scope tasks own deliveries, and a guard requires each binding's builder to be the non-design task that named that design, with the delivery's work type, application and target context, the design's security group and, for reuse, evaluation before approval expiry. These fields are additive to domain 2.0; the design profile requires their applicable presence. Migration, privilege and real currency-resolution behavior are **not yet proven**.
